# Команда ИИ для Рояля

Первая версия панели и постоянного исполнителя задач. Все роли используют официальный Codex CLI с входом через ChatGPT. Отдельный платный API и CODEX_SALE_API_KEY не используются. Лимиты подписки остаются общими с другими сеансами Codex.

Панель: https://stealth-spark-gokmxooi.expresshost.cloud/team/

## Начало работы

1. Для входа в панель ввести почту владельца и пароль. На новой установке открыть одноразовую ссылку первоначальной настройки, указать почту и задать пароль от 12 до 128 символов. Ссылка действует 24 часа и перестает работать после создания владельца. Пароль хранится как scrypt-хеш, сессия в защищенной cookie.
2. Нажать «Подключить Codex». Открыть показанную официальную страницу OpenAI, ввести одноразовый код и подтвердить вход в свой аккаунт. Пароль ChatGPT в панель вводить не нужно.
3. Открыть задачу и отправить ее на анализ. Ответить на существенные вопросы аналитика. Предложенные подзадачи можно создать отдельными карточками.
4. После анализа нажать запуск разработки. Разработчик получает требования, ответы и открытые дефекты. После завершения независимо запускается тестировщик. Ошибки автоматически возвращаются на исправление, максимум три цикла, затем требуется решение владельца.

В базе один раз создаются 22 исходные задачи с предварительными приоритетами. Анализ всего списка и разработка не запускаются автоматически. Настройка автоматического запуска разработки по умолчанию выключена.

Первой к анализу подготовлена задача по проверке списаний и зачислений. Она начнется после личного входа в Codex. Базовый прогон игры собрал проект и выполнил 203 проверки: 202 прошли, одна проверка миграции старых операций кошелька завершилась ошибкой. Точный результат добавлен в эту карточку; первопричина требует расследования. Рабочий код игры и assertions не изменялись. Выпуск остается закрытым.

Владелец явно разрешил постоянный ограниченный профиль royal-ai-worker для нового исполнителя. Профиль установлен и работает в enforce; исполнитель запущен с нулевыми внешними capabilities и no-new-privileges. Проверка настоящей изоляции успешна, available=true. Владелец настроил панель и вошел в Codex. Первый настоящий анализ завершился 9 октября 2026 в 23:45 по Москве: задача по балансу готова к разработке, сохранены четыре подзадачи и критерии приемки. Очередь работает на сервере при выключенном ноутбуке.

Сбой первого запуска устранен: Codex 0.162.0 создавал временный alias служебного помощника внутри закрытого каталога авторизации. Ограниченный адаптер bubblewrap подставляет только проверенный alias установленного native binary из доступного runtime. Остальные аргументы, файловые ограничения, дескрипторы и процесс сохраняются. Доступ к каталогу авторизации не расширен.

Карточка содержит требования, предложения подзадач, вопросы, историю исполнения, дефекты и идентификатор версии кода. Изменения кандидата сохраняются на сервере. Состояние обновляется каждые пять секунд при открытой вкладке. Пауза очереди позволяет текущему исполнителю закончить и останавливает новые запуски. Пауза конкретной карточки отзывает аренду исполнителя.

Панель использует один аккаунт владельца. Регистрация других пользователей и отправка писем не настроены. Почта нормализуется при входе, неверная почта и неверный пароль дают одинаковый отказ. Привязка почты к существующему владельцу выполняется при обслуживании через `Owner.bindEmail(email)`, без изменения хеша пароля и существующих сеансов. Скрипт `deployment/deploy-email-login.sh` принимает архив четырех файлов авторизации и почту владельца, создает резервные копии, выполняет привязку до переключения API и откатывает программу и запись владельца при ошибке.

Прогресс задачи показывает пройденные этапы, текущую подготовку, работу ИИ, сборку, серверные проверки или сохранение результата. Отдельно видны время работы, последняя активность ИИ и связь с исполнителем. Счетчик действий отражает полученные события, а не процент готовности задачи. Лимит модельного этапа отсчитывается с запуска модели и не является оценкой времени завершения. При долгом отсутствии событий панель сообщает об этом, не объявляя задачу зависшей. Старая попытка без этих данных остается без выдуманного прогресса.

Контроллер сохраняет только тип активности, время и счетчики в конкретном запуске. Команды, ответы инструментов, рассуждения и учетные данные в прогресс не попадают. Обновления защищены действующей арендой задания и версией требований; отмененный или предыдущий исполнитель не может заменить сведения текущей попытки. События объединяются в ограниченную последовательную запись, heartbeat не считается активностью модели.

Отчет тестировщика использует фиксированную важность дефекта: critical, high, medium или low. Требования к заголовку, обязательному описанию и шагам воспроизведения совпадают у модельного формата и хранилища. Неверный отчет отклоняется до сохранения; проверка ошибки второго дефекта подтверждает откат всех изменений отчета. Старые технические ошибки сохраняются в истории, известная ошибка формата важности объясняется по-русски.

При исчерпании лимита подписки задание остается в очереди и ждет следующего запуска. Перерыв на вход в аккаунт, паузу или перезапуск не удаляет частичные изменения разработчика. QA запускается только на чистой зафиксированной версии кандидата.

Браузерные проверки запускаются отдельным доверенным исполнителем на сервере. Контейнер проверки получает только одну рабочую копию кандидата, собственные процессы, Chromium и временную PostgreSQL; внешняя сеть, рабочие базы, авторизация Codex и управление Docker ему недоступны. Контроллер выбирает измененные браузерные тесты и проверки кошелька для соответствующих изменений, иначе использует существующую базовую игровую проверку. Это измеренные сценарии, а не обещание полного покрытия всех критериев: независимый тестировщик проверяет оставшиеся критерии отдельно. [Установка и ограничения](deployment/README-browser-checker.md).

Если тестирование не завершено из-за среды, отчет сохраняется вместе с конкретной недоступной проверкой. Карточка сообщает причину и ожидает повторного тестирования. Такой отчет не создает выдуманных дефектов игры и не запускает цикл исправления разработчиком. Успешная приемка по-прежнему необходима для готовности к выпуску.

## Перемещение задач на доске

Перетащи карточку за верхнюю часть или ручку ⠿, чтобы изменить ее место в колонке. Порядок сохраняется после обновления страницы. Во время перетаскивания доска подсвечивает доступные колонки и показывает место вставки.

На телефоне используй кнопку ↕ на карточке. С клавиатуры выбери эту кнопку клавишей Tab и нажми Enter. В открывшемся окне выбери колонку и место перед другой карточкой или в конце, затем нажми «Переместить».

В колонке «Нужно внимание» на карточке видна причина остановки. Нажми «Повторить запуск» или перетащи задачу на подсвеченный этап: повторится именно остановившаяся роль. Задача на паузе возвращается на сохраненный этап через «Продолжить» или перенос. Если аналитик ждет ответы, возобновление возвращает к вопросам.

Для проверенного кандидата в «Выпуске» нажми «Проверить результат». В начале карточки доступно состояние выпуска, отчет проверки находится в раскрываемом разделе «Отчеты команды». Подготовленные изменения хранятся на сервере; скачивание на компьютер не требуется. Пока отдельный исполнитель публикации не настроен, кандидат сохраняется в ожидании выпуска и изменения не установлены в игру.

На доске видны название, статус, текущая активность и причина остановки. В открытой задаче показаны четыре этапа, необходимое действие и вопросы владельцу. Описание, план, отчеты, история и расход доступны по раскрытию; дополнительные команды находятся в «Еще действия». Индикатор показывает фактический этап, время запуска и отсутствие новой активности, процент готовности и срок окончания не рассчитываются. Раскрытия и черновики ответов сохраняются при обновлении данных.

Перенос из «Входящих» в «Анализ» передает задачу аналитику. Готовую спецификацию можно перенести из «Очереди» в «Разработку», чтобы начать работу разработчика. Колонки «Тестирование» и «Выпуск» обновляются по результатам работы команды. Изменение порядка карточек на доске сохраняет приоритеты задач и порядок выбора заданий исполнителем.

## Модели и навыки ролей

В настройках панели отдельно выбираются модель, глубина рассуждения и навыки аналитика, разработчика и тестировщика. Начальные профили: gpt-6.1-sol для всех, medium для аналитика, high для разработчика и тестировщика. Каталог содержит gpt-6.1-sol, gpt-6-astra и gpt-6-luna с уровнями low, medium, high и xhigh. Доступность конкретной модели зависит от подписки на сервере. Недоступная модель вызывает понятную ошибку; платный API и скрытая подмена модели не используются.

Навыки royal-analysis, royal-development и royal-testing хранятся в role-skills как самостоятельные SKILL.md. Контроллер передает выбранные инструкции роли в доверенной части запроса и сохраняет версию и SHA-256 точного файла. Пустой выбор отключает дополнительные навыки, основные обязанности и ограничения роли сохраняются. Это учет предоставленных инструкций, а не доказательство отдельного вызова навыка моделью.

Профиль фиксируется, когда исполнитель берет шаг из очереди. Изменение настроек влияет на следующие шаги. История показывает запрошенные модель и глубину отдельно от фактических значений, прочитанных из служебных заголовков соответствующего сеанса Codex. Если эти данные недоступны или запуск был до обновления, панель сообщает об этом. Результат с наблюдаемой подменой модели или глубины отклоняется.

Для шага аналитика отведено 15 минут, разработчика 45 минут и тестировщика 30 минут. Это ограничение контроллера, а не лимит подписки. После остановки частичные изменения разработчика сохраняются. Повторная попытка получает сведения о предыдущей остановке и сначала проверяет существующие изменения. В настройках роли показано время шага; ошибки таймаута объясняются по-русски. Таймаут не вызывает бесконечные автоматические повторы.

## Границы первой версии

Реализованы анализ, вопросы, ручной запуск разработки, обязательная production-сборка, серверные тесты игры из корня server-tests во временной PostgreSQL, выбранные контроллером браузерные сценарии, отдельный запуск Codex для независимого QA и возврат дефектов. Перед QA зависимости заново устанавливаются из текущего lock-файла. Дополнительные проверки выбирает QA по критериям задачи. Отчет агента не подменяет результат обязательных проверок.

Публикация в игру отключена и в интерфейсе, и в API. Проверенный кандидат остается в отдельной рабочей копии со статусом готовности к выпуску. Исполнитель публикации требует отдельной реализации и проверки: подтверждение владельца, проверка изменений production с момента анализа, backup, выпуск проверенного образа и проверка после выпуска. Текущая панель не заявляет, что этот этап выполнен.

Снимок кода создается из серверных исходников при установке. Новые production изменения кода пока не синхронизируются автоматически. Перед анализом после внешних выпусков оператору следует обновлять исходный снимок в отсутствие активных работ, сохраняя уже созданные кандидаты. Автоматическое объединение результатов нескольких задач пока не реализовано. Поэтому один исполнитель работает последовательно, а публикация закрыта.

## Общие знания проекта

Все три роли получают [актуальную карту проекта](project-knowledge/PROJECT.md), выбранные эксплуатационные документы, собственные ответы владельца и память ответов и проверенных результатов других задач. Карта явно разделяет работающие интеграции, тестовые сервисы, подготовленный код и будущие требования. Исторические разделы документов не должны отменять более поздние подтвержденные выпуски.

Перед каждым запуском controller заново собирает разрешенные документы из /project и сохраняет отдельный снимок .factory/project-knowledge.json, доступный роли только для чтения. Это обновляет знания и у существующих рабочих копий без изменения их кода и кандидата. В отчете запуска видны версия, дата и количество доступных документов. SHA256 фиксирует использованный снимок и память решений; подмена метаданных в одном запуске отклоняется. Отсутствующие документы помечаются явно, секреты не включаются в базу знаний.

Карта и перечень источников хранятся в project-knowledge/PROJECT.md и manifest.json. После подтвержденного выпуска или нового архитектурного решения нужно обновить карту, ее версию и дату. Проверенные документы поставляются вместе с фабрикой в project-knowledge/references: часть docs существует только в локальном проекте и отсутствует в игровом каталоге VPS. Перед упаковкой обновить их из корня Рояля: `python3 ai-factory/deployment/sync-project-knowledge.py --source . --target ai-factory/project-knowledge/references`.

На сервере `python3 deployment/sync-project-knowledge.py` копирует только эти разрешенные Markdown-документы из поставленного пакета в /opt/royal-ai-project. Подготовка установки выполняет этот шаг и при существующем исходном снимке. Команда не меняет код существующих задач. Ответы владельца и успешные отчеты извлекаются из очереди перед каждым запуском автоматически; статус ready_release означает проверенный кандидат, а не опубликованный результат. Контекст ограничен по размеру и не является архивом всей переписки Codex.

Если вопрос относится к прежним неполным знаниям, для задачи с ожидаемыми ответами доступен повторный анализ. Он сохраняет уже данные владельцем ответы и заменяет незакрытые вопросы только после успешного результата нового аналитика.

## Устройство

Три отдельных сервиса Docker Compose: API с панелью, PostgreSQL для очереди и worker с Codex. Worker запускает один шаг за раз. Состояние, авторизация Codex и рабочие копии находятся в постоянных томах. Перезапуск восстанавливает просроченные задания с ограничением повторов и защищает от результатов старого исполнителя.

Запуск задач блокируется до успешной проверки настоящей Linux-изоляции и входа через ChatGPT на сервере. Кнопка подключения аккаунта доступна независимо от готовности изоляции, если worker отвечает. Наличие работающей панели само по себе не подтверждает успешное выполнение конкретной роли. Первый полный проход анализа, разработки, исправления и независимого QA проверен на задаче «Проверить списания и зачисления»: сохранен успешный отчет и статус ready_release. [Проверенный результат](deployment/VERIFICATION.md).

Ни один сервис не подключается к игровой БД. Production .env, ключ SSH, игровой data и Docker socket в исполнителя не монтируются. Исходники копируются по разрешенному списку, без symlinks, .env, приватных ключей и зависимостей. Это личная система для доверенного собственного проекта.

Для Linux worker используется отдельный ограниченный профиль AppArmor и seccomp, пользователь 1000, без внешних capabilities. Команды ролей дополнительно ограничены правилами Codex: рабочая копия и временные файлы доступны, каталоги авторизации и секретов скрыты. Аналитик работает без сети; разработчик и QA могут обращаться к локальным тестовым сервисам. Установка зависимостей имеет отдельное разрешение только на registry.npmjs.org и не запускает скрипты пакетов. Библиотеки временной PostgreSQL подготавливаются по четырем фиксированным ссылкам; их путь задается внутри изолированной команды.

Обязательные проверки controller запускает через отдельный bubblewrap: один workspace, runtime только для чтения, защищенные служебные каталоги, очищенное окружение, собственные временные файлы и локальная сеть. Доступа к внешней сети, учетным данным, другим рабочим копиям и сокетам Docker нет. Каталог /proc пустой, процессы worker через него не видны. Это позволяет исполнить настоящие тесты локальных Unix API, не расширяя разрешения модельных команд Codex.

Worker ограничен одним CPU и 1024 МБ. Для сборки Node используется heap 384 МБ. Эти ограничения проверяются на настоящей сборке проекта. Сам управляющий процесс хранит вход в Codex и обращается к OpenAI; ограничения команд ролей не следует путать с изоляцией этого доверенного процесса.

У worker включен отдельный init-процесс Docker для передачи сигналов и сбора завершившихся дочерних процессов. Это предотвращает накопление процессов Codex после повторных проверок и заполнение прежнего лимита 256 процессов. Ограничения памяти, capabilities, AppArmor и seccomp сохранены.

Путь установки: /opt/royal-ai. Отдельный снимок: /opt/royal-ai-project. Служебные секреты: /opt/royal-ai-secrets. Backup: /opt/royal-ai-backups. Caddy проксирует только /team/, остальные маршруты игры сохраняются.

Backup сохраняет dump базы очереди и состояние владельца. Рабочие копии и авторизация Codex хранятся в отдельных постоянных томах; удалять их при обновлении нельзя. Перед обновлением сохранить исходники панели, снять backup и отметить прежние образы. Восстановление очереди следует выполнять вместе с соответствующими рабочими копиями. Не переносить auth.json в исходники или переписку.

## Расход и лимиты Codex

Раздел «Расход и лимиты» показывает состояние подписки серверного исполнителя: остаток каждого доступного периода, использованный процент, время следующего обновления по Москве и свежесть проверки. На доске постоянно виден наименьший известный остаток. Лимит относится ко всему подключенному аккаунту Codex, включая работу вне этой панели. Если Codex возвращает общий счетчик токенов аккаунта, он показывается отдельно от расхода задач.

Исполнитель использует только методы чтения `account/rateLimits/read` и `account/usage/read` официального Codex app-server. Проверка не запускает модель, не сбрасывает лимиты и не покупает кредиты. Учетные данные, email, account ID, сведения о платежах и сырые ошибки не возвращаются в панель. [Протокол OpenAI](https://learn.chatgpt.com/docs/app-server).

Автоматическое чтение происходит примерно раз в минуту. Кнопка «Обновить лимиты» ставит отдельный запрос исполнителю; повторные запросы ограничены. Недоступность источника сохраняет последние полученные цифры с явным признаком устаревания. Снимок старше трех минут или прошедшее время обновления периода также считается устаревшим. Отсутствие счетчика остается неизвестным значением и не превращается в нулевой остаток.

Токены команды считаются по числам `turn.completed.usage`, которые сообщает настоящий процесс Codex. Они сохраняются в конкретном запуске до принятия результата, в том числе когда проверка результата завершилась ошибкой. Повторная запись того же расхода не увеличивает сумму. Итог равен входным и выходным токенам; кеш входит в расход входа, рассуждения входят в расход выхода. Есть разбивка по ролям, задачам и запускам.

Для старой истории используются сохранившиеся события `agent_usage`. Они обозначены как старые отчеты; им не придумывается принадлежность конкретному запуску. Запуски без счетчиков отмечены отдельно. Сумма включает только полученные значения и не является полной оценкой всех прошлых работ. Процент остатка подписки не преобразуется в число оставшихся токенов или задач.
