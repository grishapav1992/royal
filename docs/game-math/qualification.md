# Обязательная проверка математики игр

Новая игра «Сердце леса» имеет отдельную [точную модель и квалификацию реального сервера и общего кошелька](../concepts/forest-heart/server-runtime.md). Ее статус `server-qualified-client-pending` допускает проверку серверных исходников, но блокирует включение в рабочий клиентский каталог. Точный RTP лучшей стратегии: 95,994233480111%; 10 752 серверных раунда служат сверкой реализации с моделью, а не статистической оценкой RTP. Полное доказательство: [forest-heart-v1.json](qualifications/forest-heart-v1.json).

Новые правила Неополиса и Драконы ориентированы на RTP 96%. RTP считается как сумма выплат всех завершённых оплаченных раундов, делённая на сумму принятых ставок. Бесплатные продолжения входят в выплату исходного раунда и не увеличивают знаменатель. Это оценка методом моделирования, а не сертифицированный аналитический RTP и не обещание результата отдельной сессии.

## Что блокирует сборку

`npm run check:rtp` выполняется перед общей сборкой и при сборке независимых игровых модулей. Для каждой квалифицированной игры проверяются:

- правила и версия прогресса, точный список ставок и вариантов выбора;
- хеши математических исходников, серверных игровых правил и программы моделирования; CRLF и LF приводятся к одному представлению для Windows и Linux;
- совпадение политики с отчётом, минимальная выборка и независимые квалификационные seed;
- пересчитанные по первичным моментам RTP и доверительный интервал;
- оценка в пределах 96% ± 1 процентный пункт, верхняя граница интервала не выше 98%, полуширина не более 1 процентного пункта;
- сверка чистого движка с настоящими серверными `start` / `move` для 64 оплаченных раундов на каждый вариант и ставку: 1152 проверки в Неополисе и 384 в Драконе.

Для Неополиса независимая единица статистики представляет полный цикл от первоначальной команды до окончания кампании. Интервал отношения выплат к ставкам рассчитан по циклам, а не по зависимым отдельным спинам. Для Драконы единица представляет оплаченный раунд со всеми бесплатными продолжениями. Используется приближённый нормальный интервал 1,96 стандартной ошибки; это не доказательство точного теоретического значения и не оценка всех редких хвостовых событий. Seed настройки параметров отличаются от двух seed квалификации.

Новый модуль без политики RTP либо обоснованного статуса игры без ставки не собирается. Остальные 114 модулей актуального origin/main 272f566 (включая три PvP-модуля, добавленных другими чатами до первого включения этого контроля) зафиксированы в отдельном списке, а 198 файлов прежней математики защищены хешами. Это ограничение изменения исходников, а не подтверждение RTP остальных игр. Изменение защищённого исходника требует регистрации затронутых игр и новых доказательств; расширять список исключений или переписывать исходные хеши для обхода проверки запрещено. Для общей таблицы выплат необходимо охватить все использующие её игры и режимы.

## Воспроизведение

```text
npm run qualify:rtp -- --game studio-neopolis --write-proof
npm run qualify:rtp -- --game studio-dracona --write-proof
npm run check:rtp
npm run test:rtp-gate
npm run test:slot-balance
npm run build
```

Политики: `scripts/game-math/rtp-policy.json`. Успешные отчёты: [Неополис](qualifications/neopolis-v3.json), [Дракона](qualifications/dracona-v3.json). Неуспешная квалификация сохраняет диагностический результат только в игнорируемой папке `artifacts/rtp-qualification/` и завершается ошибкой. Исходники повторно сверяются перед записью отчёта. Изменять отчёт вручную для прохождения сборки нельзя. Для новой игры добавляются её полный симулятор, политика всех разрешённых режимов и серверная сверка, затем выполняется отдельная квалификация.

GitHub Actions запускает быстрый контроль на каждом PR и push в main. При изменении математических исходников, политик или доказательств отдельная матрица заново считает обе игры. Установка этих workflow сама по себе не включает защиту ветки в настройках GitHub.

При согласовании с `origin/main` 272f566 сохранены общий журнал тестового USDT и исключение неопубликованного Неополиса из рабочего каталога. У Драконы новый заголовок правил проходит через `/api/game-wallet` и приватный финансовый транспорт; старые флаги по-прежнему разрешают только прежние сохранения. Целочисленные выплаты, резерв, восстановление и отсутствие повторного начисления отдельно проверены на `NileGameRuntime`. Локальный стенд Неополиса использует отдельные одноразовые демомонеты и не подключает их к USDT.

Исторические отчёты [Неополиса v2](../../games/neopolis/math-audit.md) и [остальных слотов](slot-portfolio-review-20261023.md) оставлены с прежними результатами и версиями. Они объясняют дефект прежних правил и не описывают новую математику.

## Mortal Kombat: точная проверка банка PvP

Политика `mortal-kombat` (правила 2, прогресс 1) использует исчерпывающий повтор настоящих событий общего журнала PvP через `applyPvpMoneyEvent`. Это игра навыка, поэтому вероятности победы отдельного игрока и случайные seed не задаются. Для каждого из шести размеров ставки проверяются победы обеих сторон, оба исхода отключения, ничья, отмена, истечение срока и отказ сервера: 48 сочетаний, 144 события журнала. Во всех сочетаниях резерв обнуляется, а сумма выплат и комиссии равна исходному банку.

При результате с победителем обоим игрокам суммарно возвращается ровно 95% банка, казино получает 5%. Победителю выплачивается 1,9 его ставки. При возврате каждому возвращается его исходная ставка, комиссия равна нулю. Совокупный возврат по всем боям находится между 95% и 100% в зависимости от доли возвратов; это не утверждение о личном RTP игрока. Личный ожидаемый результат зависит от навыка и вероятности победы. Статистический доверительный интервал к этой целочисленной проверке не применяется.

Доказательство [mortal-kombat-v2.json](qualifications/mortal-kombat-v2.json) генерируется командой `npm run qualify:rtp -- --game mortal-kombat --write-proof`. Контроль сборки проверяет все ставки и исходы, актуальные хеши, адресата, выплаты, комиссию, возвраты и число проверенных событий. Старый список исключений и доказательства других игр не изменяются. Финансовая атомарность, повторная выплата, просроченная сверка и восстановление после сбоя проверяются отдельно на PostgreSQL.

## Cosmic Escape: полная серия и строгие границы RTP

После исправления проверки исходного множителя покупки Cosmic Escape зарегистрирован отдельный профиль `bounded-analytical-cosmic`: контракт правил 2 и прогресса 1, математический профиль 3. Вероятности, таблица выплат, цены 1/40/75/135 ставок, бюджеты бонусов и цель 96% ± 0,2 процентного пункта сохранены. Legacy baseline не меняется.

Квалификация охватывает обычный оплаченный спин со всеми естественными продолжениями и три покупки на каждой из 26 разрешённых ставок. Перебор 59 049 строк одной линии, рациональные вероятности символов и лучей, а также конечная цепь энергии дают точное ожидание без потолка. Условные моменты всей выплаты и направленное наружу округление ограничивают потери от потолка 10 000 ставок. Полученные границы относятся к фактическому полному раунду с потолком:

| Режим | Нижняя граница RTP | Верхняя граница RTP |
| --- | ---: | ---: |
| Normal | 95,9956% | 96,0018% |
| Cosmic Chaos | 95,9787% | 95,9847% |
| UFO Invasion | 95,8052% | 95,8332% |
| Deep Echo | 95,9062% | 95,9129% |

Отображаемые значения округлены наружу. Это детерминированные математические границы, не доверительные интервалы и не точечные оценки capped RTP. Все 104 сочетания режима и ставки входят в заданный диапазон. Кратность ставок и коэффициентов доказывает одинаковое нормализованное целочисленное начисление на каждой ставке.

В `rtp-cosmic.mjs` совместная вероятность трёх клеток колонки сохраняет зависимость от единственного портала. Для двух либо трёх первых колонок используется условная взвешенная оценка Йенсена: если `A_i` ограничивает выплату линии после известного префикса и `T = sum(A_i)`, то `E[(sum X_i)^k | prefix] <= T^(k-1) * sum(E[X_i^k | prefix] / A_i^(k-1))`. Нулевые линии исключаются. Максимумы всех 81 и 729 префиксов сверяются с полным перебором; короткий выигрыш WILD также учитывается. Моменты полной серии считаются совместно с конечным значением энергии. Для каждого конечного состояния выбирается лучшая верхняя граница потерь от потолка по порядкам 2-8, затем границы суммируются. Рациональные величины считаются точно, положительные операции с плавающей точкой округляются вверх, нижний итог RTP округляется вниз.

Программа отдельно сопоставляет независимую модель с настоящими серверными `start` / `move`: 6656 полных оплаченных раундов, по 64 на каждое сочетание режима и ставки, с двумя независимыми seed. Принудительно проверяются естественные входы через 3/4/5 порталов. Эти seed служат сверке реализации, а математические границы не зависят от случайной выборки. В ходе сверки сериализуется каждое продолжение и сопоставляются поля, линии, энергия, лучи, эхо, общая выплата и остановка серии.

Контроль сборки заново вычисляет весь аналитический сертификат и все 104 результата из программы квалификации. Метаданные модели должны совпадать с исходниками. В модели зафиксированы отдельно рассмотренные хеши всех пяти математических исходников, включая серверный движок, общий расчёт и валидатор. Это охватывает и частоты, заданные непосредственно в движке. Изменение такого исходника требует независимого пересмотра модели перед новой квалификацией. Старые доказательства других игр не меняются; неполные режимы, ставки, серверные сверки и изменённые границы отклоняются.

Быстрый gate проверяет полноту матрицы серверной сверки и формат её digest, но не восстанавливает эти digest из всех серверных траекторий. Полный повтор `qualify:rtp`, в том числе в CI, действительно выполняет все 6656 серверных раундов. Это ограничение проверки архивных метаданных сверки; математические границы заново вычисляются самим gate.

```sh
npm run qualify:rtp -- --game studio-cosmic-escape --write-proof
npm run check:rtp
npm run test:rtp-gate
```
