# Общее хранилище знаний проекта

Оба компьютера используют один граф на сервере `45.192.12.242`. Клиентские скрипты приходят из Git, а данные графа остаются на сервере. Схема ниже описывает интеграцию; наличие этих файлов в Git не означает, что сервер уже установлен. Установка и первый готовый снимок подтверждаются отдельно, затем проверяются командой `npm run brain:status`.

## Подключение компьютера

1. Получи текущие исходники по [порядку разработки](development-workflow.md). Нужны Node.js 24+ и доступный в `PATH` клиент `ssh`. uv и Python нужны только для явного локального анализа.
2. Используй собственный SSH-ключ этого устройства вне проекта. Путь по умолчанию: `~/.ssh/royal_server_ed25519`. На Windows используется домашний каталог пользователя с тем же подкаталогом `.ssh`. Если ключ уже существует, не создавай другой поверх него. Для нового устройства администратор разрешает его публичный ключ на сервере; приватный ключ не пересылается и не попадает в Git.
3. Проверь подлинность ключа сервера по известному отпечатку и сохрани его в обычном `known_hosts` этого устройства. Клиент требует `StrictHostKeyChecking=yes`: неизвестный или изменившийся сервер не принимается автоматически.
4. Выполни `npm run brain:status`. Затем проверь предметный запрос, например `npm run brain:query -- "кошелёк"`.

По умолчанию используется `root@45.192.12.242` с уже разрешённым SSH-доступом. При необходимости задай `ROYAL_BRAIN_SSH_TARGET` и `ROYAL_BRAIN_SSH_KEY` в окружении терминала. В них указываются адрес учётной записи и путь к ключу, а не сам ключ. Клиент не читает `.env`.

Например, на macOS/Linux:

```sh
export ROYAL_BRAIN_SSH_KEY="$HOME/.ssh/royal_server_ed25519"
npm run brain:status
```

На Windows PowerShell:

```powershell
$env:ROYAL_BRAIN_SSH_KEY = "$env:USERPROFILE\.ssh\royal_server_ed25519"
npm run brain:status
```

Клиент передаёт JSON только фиксированной программе:

```text
/opt/royal-project-brain/runtime/bin/node /opt/royal-project-brain/current/scripts/shared-brain-reader.mjs
```

Поддерживаются только операции чтения: `status`, `brain`, `query`, `explain`, `path`, `affected`, `god-nodes`. Клиент не отправляет произвольные серверные команды, пути к графу или команды записи. Это ограничение клиента не меняет полномочия самой SSH-учётной записи. Публичного HTTP-порта для графа нет.

## Когда обновляются знания

1. Доработка проходит обычные проверки, сохраняется в `main` и публикуется штатным процессом. Один коммит или `git push` ещё не меняет граф production.
2. После публикации запускается обязательное обслуживание `royal-dev-app-retention.service`. Оно проверяет работающий хост, состав программы, необходимые доказательства, rollback и свободное место. Только завершённый проверенный запуск получает квитанцию фактически опубликованных компонентов.
3. Квитанция связывает образ приложения, backend, опубликованные игровые пакеты и их доступные исходники с контрольными суммами. После освобождения блокировок обслуживания ставится в очередь `royal-project-brain-update.service`.
4. Сервис сверяет runtime, собирает новый граф отдельно, проверяет источники и хеши, затем повторно подтверждает работающую версию. Только после этого активный указатель переключается на завершённый снимок. Ошибка сохраняет предыдущие файлы и явно отмечает неготовность нового снимка.
5. Почасовой таймер штатного обслуживания повторно сверяет фактическое состояние и подбирает пропущенный запуск. Повтор при той же проверенной версии не требует публикации одинакового снимка. Сервис обновления также повторяется после ошибки по настройкам systemd.

Это обновление после проверенной публикации и сверки, с возможной задержкой на обслуживание и индексацию. Изменения рабочего дерева компьютера и ветки незавершённых задач не подменяют production. На втором ПК следующий запрос получает тот же активный снимок, без скачивания всей базы.

## Версии и границы знаний

`releaseId` помогает найти запись выпуска. `runtimeFingerprint` идентифицирует проверенный состав работающей программы, `snapshotId` идентифицирует конкретные артефакты графа. Хост, backend и независимые игровые модули могут иметь разные исходные коммиты. Не представляй идентификатор выпуска как единое дерево Git.

Сохранённые знания и инструкции берутся из проверенной Git-версии установленного сервиса карты. Их компонент показывает собственный коммит. Обновление знаний в `main` само по себе не заменяет установленную версию этого компонента. Статусы, даты и версии старых утверждений сохраняются. Совпавший хеш означает совпадение источника, а не новую проверку смысла утверждения; `needs_review` требует пересмотра.

Точное извлечение структуры выполняется для подтверждённых исходных входов компонента. Если доступно только частичное происхождение или разные версии одного пути, это явно отмечается предупреждением. Не выводи полноту зависимостей из отсутствующей связи. Перед чтением локального файла сверь его версию с указанным компонентом; свежий `main` может отличаться от production.

Установленный игровой пакет отражается как `published-package-only`. Его наличие не означает включение в активный каталог, разрешение прямого запуска или принятие новых раундов. Для доступности нужны действующий проверенный каталог и штатные release-проверки. Не возвращай выключенные игры на основании графа.

## Состояния и ошибки

| Состояние | Как использовать |
| --- | --- |
| `ready` | Снимок готов для подтверждённого состава компонентов. Проверяй предупреждения о покрытии и старых знаниях. |
| `missing` | Нет завершённого общего снимка. Требуется установка или первая успешная индексация. |
| `pending` | Подтверждён новый состав, его снимок ещё не готов. Обычные запросы закрыты. |
| `failed` | Последнее обновление не завершилось. Старые файлы сохранены, обычные запросы закрыты. |
| `unverified` или ошибка проверки runtime | Текущая программа не подтверждена квитанцией. Результат не считается актуальным. |

Команда состояния может завершиться с кодом 0 и показать `pending`, `failed` или `missing`: проверяй текст состояния. Обычные поисковые команды в этих случаях завершаются ошибкой. Неизвестный SSH-сервер, недоступный ключ, сеть, повреждение снимка, превышение ограничений и смена версии во время запроса также дают явную ошибку. Автоматического перехода к локальным данным и автоматических сетевых повторов в клиенте нет. Код 3 указывает неоднозначный предмет, код 4 сопровождает отсутствие результата или соответствующую ошибку проверки; читай сообщение.

Для продолжения неопубликованной доработки можно самостоятельно выбрать локальную карту:

```sh
npm run brain:build
npm run brain:query -- --local "новая доработка"
npm run graph:query -- --local "NewSymbol"
```

Она помечается как карта рабочей копии. `brain:build` и `graph:build` всегда являются локальными алиасами `build --local` и не публикуют граф на сервере. Подробности разбора находятся в [инструкции Graphify](graphify.md).

## Установка и обслуживание сервера

Сервис карты устанавливается отдельно от игрового приложения из зафиксированного коммита, уже сохранённого в GitHub. [Установщик](../deployment/knowledge/install-shared-brain.py) принимает проверенную квитанцию исходников. Runtime устанавливается отдельно; программа находится в `/opt/royal-project-brain/current`, runtime в `/opt/royal-project-brain/runtime`, данные в `/var/lib/royal-project-brain`. Нельзя считать локальный тест доказательством серверной установки.

Для работы нужны установленный сборщик квитанций в штатном обслуживании, конфигурация `/etc/royal-project-brain/enabled.json`, включённый почасовой `royal-dev-app-retention.timer` и доступный `royal-project-brain-update.service`. После установки оператор запускает штатное обслуживание и проверяет его завершённый результат, результат обновления и `ready` через тот же клиент, которым будут пользоваться чаты. Игровое приложение ради запросов к графу перезапускать не требуется.

При сбое оператор проверяет результат обслуживания, квитанцию `receipts/latest.json`, состояние сервиса обновления и `graph:status`. После устранения причины можно повторно запустить штатный сервис обновления. Не редактируй хеши, квитанции, `target.json` или активный указатель, чтобы скрыть ошибку. Диагностика и результаты не должны включать ключи, `.env`, базы или данные игроков.

Если обслуживание уже завершилось `completed`, но передача в граф завершилась ошибкой до создания квитанции, оператор может выполнить `python3 /opt/royal-maintenance/bin/automatic-retention.py --retry-project-brain /opt/royal-maintenance/automatic-runs/run-<uuid>`. Команда проверяет сохранённое доказательство завершения, заново сверяет текущую программу под блокировками публикации и повторяет только передачу в граф. Удаление истории не повторяется, новый запуск обслуживания не объявляется завершённым. Изменившаяся публикация или политика требуют обычного обслуживания.

Запрос читает и проверяет текущие файлы программы, включая зависимости и опубликованные пакеты. На медленном диске эта проверка может занимать заметное время; клиент ограничивает общий запрос восемью минутами. Проверка установки снимка не заменяет штатную проверку публикации.

Завершённые снимки лежат в `snapshots/<snapshotId>/`. `active.json` указывает текущий и предыдущий снимок. Сохраняется текущий и один предыдущий завершённый снимок; временные исходники после построения удаляются. Старые квитанции удаляются только при отсутствии ссылок на них и после защитного срока. Эти данные восстанавливаемы и не заменяют финансовые резервные копии или rollback приложения.

```sh
npm run test:graphify
npm run test:shared-brain
```

Эти проверки работают без production SSH и проверяют протокол, происхождение, атомарность, состояния и сборку на тестовых данных. Фактическая серверная проверка остаётся отдельным шагом.
