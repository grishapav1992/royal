# Подготовка выпуска

## Подготовка без резервирования сервера

Сборку исходников, RTP, проверки кошелька, браузерные тесты и передачу готового пакета выполнять без трёх общих серверных замков: `themed-publish.lock`, `.client-presentation-deploy.lock` и `module.lock`. Не занимать их ради ожидания `ready.json`, `reservation-ready.json`, решения пользователя или освобождения другого замка. Подготовку разных задач можно вести одновременно в отдельных рабочих папках.

Снимок боя для подготовки можно прочитать без замков. Это предварительный вход, который не гарантирует неизменность боя. При смене контейнера во время чтения снимок отклоняется. Защищённый установщик заново проверяет полный фактический состав под замками до изменения production и перед финансовым барьером. Чужая публикация между подготовкой и установкой вызывает отказ и новую сверку основы, а не перезапись чужих изменений.

После готовности и проверки пакета установщик пытается захватить все общие замки с `LOCK_NB`. Если хотя бы один занят, он закрывает все уже открытые дескрипторы, возвращает код 75 и сохраняет подготовленные байты. Не запускать фоновую бесконечную очередь и не повторять сборку из-за занятого замка. Повторить установку явно после согласования окна. Для `front-back-walk-20261104-v3` использовать готовый `release` либо проверенный `publish` существующего кандидата; повторный bootstrap `reserve-release` не нужен. `player-recovery-20261104-v2/reservation.py` при повторе готового пакета сохраняет исходный проверенный снимок. Обновление снимка требует отдельной переподготовки пакета.

Совместимые имена команд `reserve-release` и `reserve-publish` больше не резервируют production на время подготовки. Состояние ожидания называется `preparing_without_publication_locks`, поле `publicationLocksHeld` равно `false`. Замки удерживаются только во время защищённой серверной установки, включая сохранение отката, сборку серверного образа из проверенных файлов и финансовый барьер. Обязательное обслуживание после неё сохраняет собственные замки и проверки. Оно не выполняется внутри ожидания готовности пакета.

Новый установщик должен иметь отдельный Git-коммит и проверенные хеши в новом установочном манифесте. Готовую неизменённую сборку приложения можно сохранить: изменения только установщика не требуют повторной компиляции приложения. Не заменять исполняющийся helper, опубликованный комплект или сохранённый откат. Если установщик ещё не запускался, после обновления его Git-происхождения заново упаковать и проверить установочные метаданные. Результаты проверки блокировок: `python3 -m unittest discover -s deployment/tests -p 'test_*.py'` на Linux, с временными файлами вместо боевых путей.

## Небольшое исправление: один проверенный пакет

Для исправления интерфейса, связи или текста сначала зафиксировать его фактический состав поверх текущего боя. Небольшой размер diff сам по себе не освобождает от финансовых и математических проверок. Изменение кошелька, авторизации, правил, ставок, зависимостей, миграций или контрактов требует соответствующего полного набора проверок.

1. Завершить `work:sync` и включить проверенные исходники в main до подготовки. Получить свежий производственный маркер и выполнить `release:plan`. Если main содержит ещё не опубликованные функции, использовать проверенную проекцию, сохранив действующий каталог.
2. Выполнить `release:prepare` один раз. Повторная команда с тем же коммитом, основой, проекциями и выбором модулей проверяет и использует готовые байты. `--fresh` явно запрашивает новую сборку. Повреждённый пакет останавливает повторную подготовку; успешный старый отчёт при ошибке удаляется.
3. После подготовки сохранять HEAD выбранного коммита. Свежий `git fetch origin` и проверка включения этого коммита в main не требуют объединять новые служебные записи в уже собранный checkout. Запись развёртывания объединять после установки. Фактическое изменение боя по-прежнему требует новой сверки; чужой выпуск не перезаписывать.
4. Один раз проверить затронутое поведение и общий кошелёк: принятый раунд, потерянный ответ, прежний UUID, одно списание, восстановление, закрытие и повторное открытие. Использовать окончательные файлы, настоящий host с чатом, desktop и mobile. Обязательный общий набор: `node --import tsx scripts/database-test.ts --import tsx --test server-tests/game-wallet.test.ts server-tests/wallet-account.test.ts server-tests/round-precision.test.ts`. Он дополняет проверку готового host, а не заменяет её. Для неизменных байтов и входов повторять тот же сценарий не требуется. В записи проверки указать коммит, хеши готовых файлов, команду и результат. При изменении затронутого входа повторить соответствующий сценарий.
5. Перед передачей пакета выполнить `release:verify -- --github`. Команда один раз проверяет выпуск после свежего fetch, сверяет все байты и состав папок, происхождение исходников, патчи и включение в main. Квитанция также фиксирует SHA-256 манифеста. Использовать результат в штатном установщике, без новой сборки и без отдельного повторного `check`, если выполняется его защищённая операция `release`.
6. Установщик сохраняет исходники и образ для отката, сверяет бой до сборки образа и ещё раз перед финансовым барьером публикации. Проверка действующего кошелька и барьер не кэшируются. После установки обязательны публичная доступность, версия файлов, прежний каталог и отсутствие повторного дебета в затронутом сценарии.
7. После освобождения замков выполнить обязательное обслуживание. Для точного неизменяемого образа можно использовать приватное подтверждение полного чтения его файлов, связанное с ID образа, хешем программы проверки и полным ожидаемым инвентарём. Изменение любого из этих значений требует нового чтения. Работающие файлы, настройки, модули и службы проверяются заново непосредственно перед удалением истории и после него. Проверенный откат, финансовые резервные копии, включённый таймер и запас диска остаются обязательными.

Не повторять всю математику, все компоновки игр и одну и ту же ручную проверку только из-за fetch, записи о публикации или смены служебного комментария. Обязательная проверка RTP в сборке остаётся. Изменённая математика, игра, транспорт денег или контракт требуют своих математических, совместимых и финансовых тестов. Ошибка, изменённые входы или новые сомнения являются основанием для дополнительных проверок. Ожидание чужого выпуска и нехватка ресурсов хостинга отражаются отдельно от времени работы инструментов; фиксированное время установки не гарантируется.

Получение актуальных исходников, локальная разработка, передача фичи между устройствами и сохранение в GitHub описаны в [общем рабочем процессе](development-workflow.md). Начинать публикацию только после включения проверенных исходников в main.

Работа над разными задачами ведётся в отдельных чистых worktree от свежего `origin/main`. Незавершённые изменения других чатов не переносятся в выпуск. Состояние основной рабочей папки не является версией для публикации.

## Состав игр в выпуске

Основа выпуска: фактический действующий каталог боевой версии. Наличие игры в исходниках, `origin/main`, старом выпуске или реестре модулей не разрешает открывать её игрокам.

Удалённые, скрытые, архивные и отключённые игры остаются недоступными, пока пользователь прямо не попросит вернуть конкретные игры. Это правило действует и для другого названия, другого каталога, прямого запуска и API новых раундов. Новые игры добавляют только в рамках поставленной пользователем задачи. Обновление отдельной игры или общей функции не разрешает менять доступность остальных игр.

До установки сравнить доступность игр с текущей боевой версией. Для каждого добавления или возвращения указать соответствующий запрос пользователя в записи выпуска. Изменения без такого основания исключить. Если доработка зависит от отключённой игры, использовать действующие игры либо сообщить об ограничении. Сохранение и завершение уже принятых раундов не должно повторно открывать игру для новых ставок.

## Один коммит и одна сборка

1. Получить свежий main, согласовать собственные изменения, выполнить проверки задачи и сохранить исходники в Git. Перед производственной подготовкой отправить их в `origin/main`.
2. Взять коммит исходников текущего боя из проверенной записи `deployment/SERVER.md`. `origin/main` не заменяет этот маркер: в нём могут находиться ещё не опубликованные изменения. Проверить фактический серверный состав по обычным правилам публикации.
3. Просмотреть разницу: `npm run release:plan -- --base <production-commit>`.
4. Подготовить приложение: `npm run release:prepare -- --base <production-commit>`. Для отдельных совместимых игр: `npm run release:prepare -- --base <production-commit> --modules royal-dice,cr-vs-leo`.
5. Выполнить проверки конкретной доработки, кошелька, повторного открытия и настоящего host с чатом на телефоне и компьютере. Перед передачей файлов установщику запустить `npm run release:verify`.
6. Перед публикацией снова получить свежий main и сравнить сервер с проверенной основой под существующими замками. Использовать подготовленные файлы с проверенными SHA-256 и существующий защищённый установщик. После установки выполнить публичные проверки и сохранить запись выпуска в GitHub.
7. После освобождения замков запустить `royal-dev-app-retention.service` по `deployment/maintenance/README.md`. Проверить `status: completed` в `/opt/royal-maintenance/last-result.json`, включённый почасовой таймер, сохранность текущего выпуска и одного проверенного комплекта отката, готовность приложения и минимум 5 GiB свободного места. Пропуск или ошибка очистки означает незавершённое обслуживание выпуска: выяснить причину и довести проверку до результата.

Подготовка требует чистого checkout, включая отсутствие неотслеживаемых исходников. Она получает свежий `origin/main` и проверяет, что выбранный коммит уже включён в него. `--local` разрешает подготовку коммита для локального review или CI без проверки GitHub; манифест явно содержит `githubVerified: false`. Этот флаг не подтверждает готовность к публикации.

Для готового артефакта CI из main восстановить перечисленные в манифесте файлы в чистый checkout того же коммита и выполнить `npm run release:verify -- --github`. Команда проверит файлы, получит свежий main и запишет отдельную квитанцию `module-build/release-github.json`, сохранив исходный манифест. Повторная сборка для этой проверки не нужна. Установщик по-прежнему должен сверить фактическую боевую основу и применить штатные ограничения.

Выбор `--modules` ограничивает выходные пакеты. Он не доказывает, что остальные изменения между базой и коммитом можно не выпускать. При изменении host-контракта, серверных правил или общего кода проверить совместимость с фактически установленным host. Список `changed` в манифесте всегда включает полную разницу коммитов. Обновление сервера, зависимостей, Go-программ, миграций или конфигурации требует соответствующего обычного процесса публикации; команда подготовки не заменяет его.

## Результат без копий проекта

Если действующий клиент сохраняет версии исходников, отличающиеся от ещё не опубликованного main, подготовка приложения поддерживает явный `--host-projection <tracked-json-path>`. Конфигурацию сначала проверяют, коммитят и включают в main. Она задаёт производственную основу, точные достижимые Git-источники, исходные и итоговые SHA-256 и однократные изменения разрешённых файлов. Неизвестный используемый исходник останавливает сборку.

Этот режим собирает только основной клиент прямо в штатный `dist`, сохраняя источник каждого входа в первоначальном манифесте выпуска. Административный клиент и прежние статические ресурсы остаются в проверенном родительском образе. `release:verify` повторно проверяет конфигурацию и все использованные исходники; производственная основа должна совпадать с `--base`. После проверки повторная клиентская сборка не требуется. Сверка живого сервера и защищённая установка остаются обязательными.

Для узкого изменения основного backend можно отдельно указать `--backend-projection <tracked-json-path>`, в том числе вместе с `--host-projection`. Формат конфигурации тот же: `format: 1`, `productionCommit`, `files` с точными Git-источниками, исходными и итоговыми SHA-256 и необязательными однократными `patches`. Поле `entries` для backend обязано быть `['server/index.ts']`. Конфигурация сначала включается в main. В `files` должны присутствовать также `package.json` и `tsconfig.json`; значения, влияющие на зависимости и разрешение пакетов, должны совпадать с рабочей конфигурацией. Команды тестов могут отличаться. Неявные `extends` и `references` для backend-конфигурации не поддерживаются.

Backend-проекция читает исходники через тот же проверяемый Git-reader, отклоняет неизвестные входы, недостижимые коммиты, несовпадающие хеши, неподтверждённые внешние пакеты и символические ссылки. Она создаёт только `dist-server/index.js`. Обычный этап сборки основного backend в этом режиме пропускается, поэтому другой состав HEAD не перезаписывает подготовленный файл. Остальные обязательные этапы подготовки сохраняются. Выпуск только модулей не поддерживает проекции.

Манифест сохраняет `backendProjection` в корне и в отчёте сборки: путь и SHA-256 конфигурации, производственную основу, единственный вход, полный перечень использованных исходников с Git-происхождением и SHA-256 выходного файла. Поле `graphSha256` связывает конфигурацию с полным упорядоченным инвентарём входов и их происхождения. Тот же отпечаток записан в служебный комментарий подготовленного `index.js`. Удаление зависимости из отчёта или замена отпечатка обнаруживаются без повторной сборки. `release:verify` повторно проверяет эти записи, исходники, комментарий и совпадение выходного хеша с общим инвентарём. Перед публикацией отдельно сверяют, что математические доказательства относятся к фактически использованным проецированным исходникам. Проекция не разрешает включать посторонние изменения в установочный пакет и не заменяет финансовые, миграционные или серверные проверки.

Команда использует штатные `dist`, `dist-server`, `module-dist` и `module-build`. Она не создаёт копии исходников, зависимостей, базы или `.env`. Выходные файлы перечислены в `module-build/release-manifest.json`: коммит и дерево исходников, производственная база, список изменений, точные версии пакетов и SHA-256. В манифест не попадают `.env`, секреты или пользовательские данные. Старые версии модулей исключены из состава выпуска, но локально сохраняются для возможных открытых сессий.

`release:verify` проверяет коммит, чистоту исходников, все байты и состав каталогов. Изменённые исходники, повреждение ресурса, лишний файл пакета или другая сборка приводят к отказу. Блокировка исключает две одновременные подготовки в одном checkout. Не запускайте обычную сборку параллельно с подготовкой в том же checkout; итоговая проверка также обнаруживает несовпадение результатов. Неудачная подготовка удаляет прежний успешный манифест, оставляет отчёт об ошибке и освобождает свою блокировку.

`module-build/application-report.json` показывает длительность RTP-проверки, проверки типов, модулей, host и трёх серверных программ. `release-timings.json` добавляет время GitHub и составления инвентаря. Это фактические замеры текущего запуска, без обещания одинаковой скорости сервера или сети.

## Повторные сборки

Обычные игровые пакеты используют общий локальный кэш всех worktree одного Git-репозитория: `<git-common-dir>/royal-module-cache/v1`. После промаха собственного `module-build` сборщик проверяет общую запись и восстанавливает отдельные файлы пакета и локальное доказательство, сохраняя обычные `module-dist` и `release:verify`. Жёстких ссылок между кэшем и рабочими выходами нет: повреждение файла одного чата не меняет пакет другого. Имя рабочей папки и HEAD не являются ключом кэша; ключ включает фактические входы, конфигурацию, зависимости, инструментарий, ресурсы и контракт. Дополнительно заново проверяются все хеши `sourceFiles` и каждый выходной байт. Новый кандидат разрешения импорта и новый допустимый ресурс сбрасывают попадание. Повреждённый пакет или конфликт неизменяемой локальной версии вызывают отказ, а не перезапись.

В общем кэше хранится один атомарный файл на игру, без истории исходников, зависимостей, настроек и данных пользователей. Новая версия заменяет предыдущую запись игры. По умолчанию установлен общий лимит 2 GiB и сохраняется не менее 10 GiB свободного места. Если лимит или резерв не позволяют запись, сборка остаётся рабочей, запись пропускается. Чтение не захватывает замки. Для короткой атомарной записи применяется отдельный локальный маркер; занятость пропускает запись без ожидания и никогда не удерживает серверные замки. Прерванный писатель может оставить `.write-lock/owner.json`: действующие записи остаются читаемыми, новые сборки не блокируются. Удалять такой маркер разрешено только после подтверждения завершения указанного процесса и отсутствия других писателей.

`ROYAL_SHARED_MODULE_CACHE=0` отключает общий кэш; `ROYAL_SHARED_MODULE_CACHE_DIR` задаёт отдельную папку, `ROYAL_SHARED_MODULE_CACHE_MAX_BYTES` задаёт лимит. В одноразовом CI общий кэш по умолчанию выключен, сохраняется существующий Actions-кэш обычных пакетов. `--force` не читает ни локальный, ни общий кэш, но сохраняет заново проверенный обычный результат. Проекционные пакеты по-прежнему собираются из явно проверенных Git-источников и в общий кэш не входят. Математический допуск и проверка RTP выполняются при каждом запуске до чтения пакетов из кэша; финансовые и производственные проверки этим механизмом не заменяются.

В `module-build/build-report.json` поля `cache.localHits`, `cache.sharedHits`, `cache.writes` и строки `cacheSource` показывают фактическое переиспользование. `timings.rtpDurationMs` отделяет обязательную математическую проверку от `timings.packagesDurationMs`. Сравнивать холодный запуск и восстановление общего пакета нужно на одинаковых входах и отдельно показывать обе длительности. Старое суммарное время этапа `modules` включает RTP и не является временем одной компиляции.

Для выборочного обновления независимых игр поверх сохранённой production-основы host-проекция может задать `moduleGames` и `moduleAssets`. Первый список фиксирует обновляемые пакеты, второй содержит хеши существующих публичных ресурсов. Подготовка сначала строит полный каталог пакетов, затем пересобирает только выбранные игры через `--source-projection` из проверенных Git-источников. Общие импорты оформления тоже берутся из проекции. Источники читаются в памяти, без замены рабочих файлов. Проекционный пакет не использует обычный кэш модулей. Отчёт `build.moduleProjection` связывает происхождение входов, общий host-мост, изображения, манифесты и итоговые файлы; остальные пакеты остаются в общем инвентаре. Scoped-установщик отдельно проверяет эти связи перед публикацией. Изменение внешних указателей игр выполняется штатным publisher после установки совместимого host.

`npm run build` сохраняет все прежние обязательные этапы и математическую проверку. Сборщик модулей повторно использует готовую версию только после сверки её исходников, конфигурации, версии инструментария, зависимостей, каталогов разрешения импортов, всех заявленных медиаресурсов и точных выходных байтов. Изменение общего входа пересобирает зависимые игры. Новые файлы в динамическом каталоге ресурсов и новые кандидаты импортов также сбрасывают кэш. Пропавший каталог пакета пересобирается; повреждённая неизменяемая версия вызывает отказ.

Для нескольких игр используется одна команда: `node scripts/build-game-module.mjs --games royal-dice cr-vs-leo`. `--force` повторяет сборку без кэш-попаданий и по-прежнему проверяет неизменяемость существующей версии. `module-build/build-report.json` содержит количество собранных и повторно использованных пакетов и время каждой игры. Доказательства кэша являются локальным ускорением сборки, а не границей доверия для публикации.

## CI

Изменения только в Markdown-инструкциях, заметках и `deployment/SERVER.md` получают короткую проверку состава без новой сборки приложения. Если к ним добавлена только `deployment/releases/<release>/verification.json`, выполняются проверки инструментов выпуска и обслуживания. При любом изменении кода, денег, математики, контрактов, ресурсов, зависимостей, тестов, CI или неизвестного пути сохраняется полный процесс ниже. Короткая проверка требует успешного завершения этого CI для предшествующего коммита main. Если его проверка ещё идёт, завершилась ошибкой, недоступна через API, либо Git-основа отсутствует или не подтверждена, включается полный процесс. Запись о выпуске сразу после непроверенного изменения кода не позволяет обойти его проверки. Переименование кода в документ учитывает удалённый исходный путь и не позволяет выбрать короткую проверку. Полный CI отдельно выполняет обязательный общий набор кошелька.

GitHub Actions выполняет одну подготовку приложения, математические и инструментальные проверки, проверки пакетов и существующие проверки баланса. Сборка уже включает проверку типов и RTP, поэтому отдельные дубли этих команд убраны из этого job. Кэш сохраняет пакеты и доказательства сборки, но никогда не отменяет проверку входов и выходов. Готовые файлы, манифест и замеры доступны как `release-<commit>` три дня. Кэш и загрузка артефактов настроены по документации [actions/cache](https://github.com/actions/cache) и [actions/upload-artifact](https://github.com/actions/upload-artifact).

Только в одноразовом CI checkout, после тестов, удаляются неактивные версии пакетов перед сохранением кэша. Локальные версии и боевой каталог этим инструментом не очищаются. CI не имеет ключа SSH и не публикует приложение автоматически. Устаревшие проверки pull request отменяются; уже начатая сборка main завершается вместе с загрузкой артефакта, даже если другой чат отправил следующий коммит. Это не затрагивает производственную установку.

## Совместимые пакеты для действующего host

Для узкого выпуска модулей поддерживается `--module-projection <tracked-json-path>` вместе с `--modules`. Конфигурация перечисляет точные Git-источники, хеши действующих ресурсов, производственную основу и выбранные пакеты. Если в main уже изменён progress-контракт, более ранний контракт задаётся явно в `moduleContracts` и должен совпасть с производственным. Идентичность, API и правила не меняются. Штатный установщик отдельно проверяет точное совпадение с установленным host. Проверка выпуска повторно сверяет происхождение, полный граф исходников, отпечаток сборщика, математическую политику, ресурсы и отпечатки пакетов. Этот режим не публикует основной клиент или backend и не разрешает расширять каталог.
