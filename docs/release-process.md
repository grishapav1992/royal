# Подготовка выпуска

Получение актуальных исходников, локальная разработка, передача фичи между устройствами и сохранение в GitHub описаны в [общем рабочем процессе](development-workflow.md). Начинать публикацию только после включения проверенных исходников в main.

Работа над разными задачами ведётся в отдельных чистых worktree от свежего `origin/main`. Незавершённые изменения других чатов не переносятся в выпуск. Состояние основной рабочей папки не является версией для публикации.

## Один коммит и одна сборка

1. Получить свежий main, согласовать собственные изменения, выполнить проверки задачи и сохранить исходники в Git. Перед производственной подготовкой отправить их в `origin/main`.
2. Взять коммит исходников текущего боя из проверенной записи `deployment/SERVER.md`. `origin/main` не заменяет этот маркер: в нём могут находиться ещё не опубликованные изменения. Проверить фактический серверный состав по обычным правилам публикации.
3. Просмотреть разницу: `npm run release:plan -- --base <production-commit>`.
4. Подготовить приложение: `npm run release:prepare -- --base <production-commit>`. Для отдельных совместимых игр: `npm run release:prepare -- --base <production-commit> --modules royal-dice,cr-vs-leo`.
5. Выполнить проверки конкретной доработки, кошелька, повторного открытия и настоящего host с чатом на телефоне и компьютере. Перед передачей файлов установщику запустить `npm run release:verify`.
6. Перед публикацией снова получить свежий main и сравнить сервер с проверенной основой под существующими замками. Использовать подготовленные файлы с проверенными SHA-256 и существующий защищённый установщик. После установки выполнить публичные проверки и сохранить запись выпуска в GitHub.

Подготовка требует чистого checkout, включая отсутствие неотслеживаемых исходников. Она получает свежий `origin/main` и проверяет, что выбранный коммит уже включён в него. `--local` разрешает подготовку коммита для локального review или CI без проверки GitHub; манифест явно содержит `githubVerified: false`. Этот флаг не подтверждает готовность к публикации.

Для готового артефакта CI из main восстановить перечисленные в манифесте файлы в чистый checkout того же коммита и выполнить `npm run release:verify -- --github`. Команда проверит файлы, получит свежий main и запишет отдельную квитанцию `module-build/release-github.json`, сохранив исходный манифест. Повторная сборка для этой проверки не нужна. Установщик по-прежнему должен сверить фактическую боевую основу и применить штатные ограничения.

Выбор `--modules` ограничивает выходные пакеты. Он не доказывает, что остальные изменения между базой и коммитом можно не выпускать. При изменении host-контракта, серверных правил или общего кода проверить совместимость с фактически установленным host. Список `changed` в манифесте всегда включает полную разницу коммитов. Обновление сервера, зависимостей, Go-программ, миграций или конфигурации требует соответствующего обычного процесса публикации; команда подготовки не заменяет его.

## Результат без копий проекта

Если действующий клиент сохраняет версии исходников, отличающиеся от ещё не опубликованного main, подготовка приложения поддерживает явный `--host-projection <tracked-json-path>`. Конфигурацию сначала проверяют, коммитят и включают в main. Она задаёт производственную основу, точные достижимые Git-источники, исходные и итоговые SHA-256 и однократные изменения разрешённых файлов. Неизвестный используемый исходник останавливает сборку.

Этот режим собирает только основной клиент прямо в штатный `dist`, сохраняя источник каждого входа в первоначальном манифесте выпуска. Административный клиент и прежние статические ресурсы остаются в проверенном родительском образе. `release:verify` повторно проверяет конфигурацию и все использованные исходники; производственная основа должна совпадать с `--base`. После проверки повторная клиентская сборка не требуется. Сверка живого сервера и защищённая установка остаются обязательными.

Для узкого изменения основного backend можно отдельно указать `--backend-projection <tracked-json-path>`, в том числе вместе с `--host-projection`. Формат конфигурации тот же: `format: 1`, `productionCommit`, `files` с точными Git-источниками, исходными и итоговыми SHA-256 и необязательными однократными `patches`. Поле `entries` для backend обязано быть `['server/index.ts']`. Конфигурация сначала включается в main. В `files` должны присутствовать также `package.json` и `tsconfig.json`; значения, влияющие на зависимости и разрешение пакетов, должны совпадать с рабочей конфигурацией. Команды тестов могут отличаться. Неявные `extends` и `references` для backend-конфигурации не поддерживаются.

Backend-проекция читает исходники через тот же проверяемый Git-reader, отклоняет неизвестные входы, недостижимые коммиты, несовпадающие хеши, неподтверждённые внешние пакеты и символические ссылки. Она создаёт только `dist-server/index.js`. Обычный этап сборки основного backend в этом режиме пропускается, поэтому другой состав HEAD не перезаписывает подготовленный файл. Остальные обязательные этапы подготовки сохраняются. Выпуск только модулей не поддерживает проекции.

Манифест сохраняет `backendProjection` в корне и в отчёте сборки: путь и SHA-256 конфигурации, производственную основу, единственный вход, полный перечень использованных исходников с Git-происхождением и SHA-256 выходного файла. Поле `graphSha256` связывает конфигурацию с полным упорядоченным инвентарём входов и их происхождения. Тот же отпечаток записан в служебный комментарий подготовленного `index.js`. Удаление зависимости из отчёта или замена отпечатка обнаруживаются без повторной сборки. `release:verify` повторно проверяет эти записи, исходники, комментарий и совпадение выходного хеша с общим инвентарём. Перед публикацией отдельно сверяют, что математические доказательства относятся к фактически использованным проецированным исходникам. Проекция не разрешает включать посторонние изменения в установочный пакет и не заменяет финансовые, миграционные или серверные проверки.

Команда использует штатные `dist`, `dist-server`, `module-dist` и `module-build`. Она не создаёт копии исходников, зависимостей, базы или `.env`. Выходные файлы перечислены в `module-build/release-manifest.json`: коммит и дерево исходников, производственная база, список изменений, точные версии пакетов и SHA-256. В манифест не попадают `.env`, секреты или пользовательские данные. Старые версии модулей исключены из состава выпуска, но локально сохраняются для возможных открытых сессий.

`release:verify` проверяет коммит, чистоту исходников, все байты и состав каталогов. Изменённые исходники, повреждение ресурса, лишний файл пакета или другая сборка приводят к отказу. Блокировка исключает две одновременные подготовки в одном checkout. Не запускайте обычную сборку параллельно с подготовкой в том же checkout; итоговая проверка также обнаруживает несовпадение результатов. Неудачная подготовка удаляет прежний успешный манифест, оставляет отчёт об ошибке и освобождает свою блокировку.

`module-build/application-report.json` показывает длительность RTP-проверки, проверки типов, модулей, host и трёх серверных программ. `release-timings.json` добавляет время GitHub и составления инвентаря. Это фактические замеры текущего запуска, без обещания одинаковой скорости сервера или сети.

## Повторные сборки

`npm run build` сохраняет все прежние обязательные этапы и математическую проверку. Сборщик модулей повторно использует готовую версию только после сверки её исходников, конфигурации, версии инструментария, зависимостей, каталогов разрешения импортов, всех заявленных медиаресурсов и точных выходных байтов. Изменение общего входа пересобирает зависимые игры. Новые файлы в динамическом каталоге ресурсов и новые кандидаты импортов также сбрасывают кэш. Пропавший каталог пакета пересобирается; повреждённая неизменяемая версия вызывает отказ.

Для нескольких игр используется одна команда: `node scripts/build-game-module.mjs --games royal-dice cr-vs-leo`. `--force` повторяет сборку без кэш-попаданий и по-прежнему проверяет неизменяемость существующей версии. `module-build/build-report.json` содержит количество собранных и повторно использованных пакетов и время каждой игры. Доказательства кэша являются локальным ускорением сборки, а не границей доверия для публикации.

## CI

GitHub Actions выполняет одну подготовку приложения, математические и инструментальные проверки, проверки пакетов и существующие проверки баланса. Сборка уже включает проверку типов и RTP, поэтому отдельные дубли этих команд убраны из этого job. Кэш сохраняет пакеты и доказательства сборки, но никогда не отменяет проверку входов и выходов. Готовые файлы, манифест и замеры доступны как `release-<commit>` три дня. Кэш и загрузка артефактов настроены по документации [actions/cache](https://github.com/actions/cache) и [actions/upload-artifact](https://github.com/actions/upload-artifact).

Только в одноразовом CI checkout, после тестов, удаляются неактивные версии пакетов перед сохранением кэша. Локальные версии и боевой каталог этим инструментом не очищаются. CI не имеет ключа SSH и не публикует приложение автоматически. Устаревшие проверки pull request отменяются; уже начатая сборка main завершается вместе с загрузкой артефакта, даже если другой чат отправил следующий коммит. Это не затрагивает производственную установку.
