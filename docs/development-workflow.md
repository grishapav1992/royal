# Разработка с разных устройств

GitHub `grishapav1992/royal` хранит общие исходники. `main` является общей основой разработки; запись в `deployment/SERVER.md` определяет, какая версия опубликована на сервере. Незавершённая фича хранится в отдельной ветке. Каждый компьютер использует собственный checkout и собственные настройки окружения.

## Перед каждой новой фичей

В чистом checkout ветки main выполнить `npm run work:start -- <feature-name>`, например `npm run work:start -- chat-recovery`.

Команда показывает состояние Git, получает свежий origin/main, обновляет реальные рабочие файлы main только быстрым продвижением и создаёт ветку `feature/chat-recovery` от полученного main. Она работает до установки npm-зависимостей. Затем установить или обновить зависимости по `package-lock.json` через `npm ci` и делать изменения локально.

Если в папке есть незавершённая работа, команда остановится после получения GitHub. Файлы сохраняются. Для независимой задачи агент создаёт отдельный managed worktree от свежего origin/main согласно `AGENTS.md`. Не копировать весь проект, зависимости, `.env`, базы или ключи в очередной staging-каталог. Свободное место и условия очистки учитывать по действующим правилам проекта.

`npm run work:sync` обновляет уже существующую чистую рабочую ветку. В main допускается только быстрое продвижение; локальные неопубликованные коммиты main требуют отдельного согласования. В ветке фичи команда сначала объединяет сохранённую на GitHub версию той же ветки, затем актуальный main. При расхождении истории сохраняются обе стороны через merge. Опубликованные коммиты не переписываются. Конфликт останавливает работу до его разрешения; автоматические stash, reset, clean и force-push не используются.

## Передача незавершённой фичи на другое устройство

На первом устройстве сохранить только файлы своей задачи обычным коммитом и отправить ветку, например `git push -u origin feature/chat-recovery`. Незавершённую фичу не включать в main ради переноса между компьютерами.

На втором устройстве получить свежие ссылки через `git fetch origin` и открыть эту же ветку: `git switch --track origin/feature/chat-recovery`. Если локальная ветка уже существует, переключиться на неё и выполнить `npm run work:sync`. После синхронизации обновить зависимости по lock-файлу и продолжать работу. При одновременном изменении одних файлов конфликты нужно разрешить явно; Git не может решить смысловые противоречия вместо разработчика.

Для нового компьютера исходники получают через `git clone https://github.com/grishapav1992/royal.git`. Настройки `.env`, доступ к GitHub и серверные SSH-права настраиваются отдельно. Секреты, ключи, зависимости и рабочие данные через Git не передаются. Обычная разработка не требует доступа к боевому серверу; публикацию выполняет устройство с разрешённым доступом.

## Завершение и публикация

1. Сохранить изменения своей задачи в ветке фичи. Перед отправкой выполнить `npm run work:sync`: это получает main и изменения той же ветки с других устройств и включает их в рабочие файлы.
2. Разрешить конфликты, если они появились, и повторить проверки на итоговой версии. Сохранить результат и отправить ветку в GitHub.
3. Включить готовую проверенную фичу в main через обычное объединение или pull request. Перед интеграцией снова получить GitHub, сохранить новые изменения других разработчиков и выполнить нужные повторные проверки. Устаревшее состояние main не перезаписывать. При прямой отправке чистой согласованной ветки использовать обычный `git push origin HEAD:main`; отказ при изменившемся main требует новой сверки, без force-push.
4. Подготовить выпуск из конкретного коммита, уже сохранённого в main, по `docs/release-process.md`. Использовать готовый CI-артефакт либо штатную подготовку и проверку манифеста. Сверить фактическую боевую основу и совместимость. Не публиковать вместе с задачей чужие незавершённые изменения.
5. Установить проверенную сборку существующим защищённым установщиком. Сохранить production-конфигурацию и данные. После публичных проверок записать коммит, идентификатор выпуска и результат в `deployment/SERVER.md`, затем отправить запись в GitHub.

Получается последовательность: свежие исходники из GitHub, локальная разработка, сохранение готовой фичи в main, сборка из этого коммита, установка на сервер, запись результата в GitHub. Следующее устройство начинает с новой сверки GitHub. Сохранение коммита в main и установка на сервер являются отдельными этапами.

## Хранение на ПК

На ПК остаётся одна текущая рабочая папка проекта. История исходников хранится в GitHub. Незавершённые изменения перед уборкой сохраняются отдельным коммитом в ветке фичи или WIP и отправляются в GitHub. Нужно проверить удалённый коммит, а не только локальную ветку. Непроверенные черновики не включают в main ради освобождения диска.

Постоянные локальные резервные ZIP/TAR, полные staging-копии проекта, копии зависимостей и папки завершённых задач не создаются и не сохраняются. Изолированный Git worktree используют только на время действительно одновременной работы. После сохранения исходников в GitHub лишний worktree удаляют вместе с принадлежащими задаче временными сборками и материалами проверок. Текущие исходники, рабочие зависимости и обычные каталоги сборки используют повторно.

У каждой временной папки в artifacts/work должен быть владелец, назначение и условие удаления. В конце задачи удаляют её устаревшие архивы выпуска, дубли сборок, скриншоты, трассировки, видео и журналы; при необходимости оставляют небольшой итоговый отчёт. Активную работу другого чата и файлы, изменившиеся после инвентаризации, сначала сохраняют и проверяют. Нельзя очищать весь artifacts одной командой.

Текущие .env, ключи и необходимые локальные данные сохраняются отдельно от Git. Их нельзя загружать в репозиторий для замены резервной копии. Правило касается хранения проекта на ПК и не отменяет серверные резервные копии базы, финансовых данных, постоянных томов и проверенный набор отката production.
