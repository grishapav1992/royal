# Адресная очистка тестового аудита

Очистка использует отдельное служебное подключение из `ROYAL_AUDIT_CLEANUP_DB_URL_FILE`. У роли отчётности остаётся доступ через ограниченные функции. Для установки и переключения используются разрешённые имена схем на одной базе, права на схему аудита и достаточные права чтения и блокировки исходных таблиц. Предел временных файлов подключения составляет 64 МиБ. Настройки TLS совпадают с другими служебными командами аудита.

Установите журнал очистки командой `install`. Для нового тестового среза используйте `start-test`. Перед планированием остановите наблюдатель тестового набора, дождитесь завершения принятых операций и закройте набор командой `seal`. Все команды со схемой источников принимают необязательный `--payments-schema` для настроенного платёжного контура.

## Остановка захвата проводок

Если требуется остановить и транзакционный захват, используйте отдельную команду с точным ID, окружением и теми же исходными схемами, с которыми открыли набор. Учётной записи нужны права владельца исходных таблиц для отключения их триггеров.

```sh
npm run --silent audit:cleanup -- stop-capture --schema royal_audit --game-schema royal_game \
  --dataset '<dataset UUID>' --environment test
```

Команда закрывает выбранный набор и отключает его триггеры одной транзакцией. При занятом исходном журнале она завершится с `source-busy`, а набор и триггеры сохранят прежнее состояние. Повтор для того же набора сохраняет исходную отметку закрытия. Рабочий набор требует явного `--environment live`. Команда для старого набора не может остановить захват активного.

Сначала отключите технический наблюдатель в игровом процессе или снимите его настройки при следующем запуске. Остановка в PostgreSQL прекращает приём аудиторских записей для закрытого UUID даже при запущенном наблюдателе. Уже принятые обязательства продолжают рассчитываться каноническим кошельком. Если расчёт откатился из-за сбоя записи ссылки аудита, после остановки его можно повторить с исходным ID. Следующий набор получает новый снимок остатков и включает триггеры при открытии. Проводки за интервал остановки остаются в исходных журналах.

## Файлы тестовых выгрузок

Создайте отдельный абсолютный каталог с правами `0700` для управляемых экспортов. Команда `init-files` создаёт каталог точного тестового UUID и возвращает путь для выходных файлов `player` и `replay`. Готовую выгрузку зарегистрируйте командой `register-file`. Она связывает имя, размер, SHA-256 и идентификатор файла с набором. Пользовательские копии за пределами этого каталога остаются внешними.

```sh
npm run --silent audit:cleanup -- init-files --schema royal_audit \
  --dataset '<test UUID>' --files-root '/absolute/private/audit-exports'
npm run --silent audit:cleanup -- register-file --schema royal_audit \
  --dataset '<test UUID>' --files-root '/absolute/private/audit-exports' --name postings.csv
```

Поддерживаются обычные приватные CSV и JSON, максимум 128 файлов, 64 МиБ на файл и 256 МиБ суммарно. Символические и жёсткие ссылки, незарегистрированные объекты и изменённые файлы блокируют работу с каталогом.

## Проверка и применение

```sh
npm run --silent audit:cleanup -- install --schema royal_audit --game-schema royal_game
npm run --silent audit:cleanup -- seal --schema royal_audit --game-schema royal_game --dataset '<test UUID>'
npm run --silent audit:cleanup -- plan --schema royal_audit --game-schema royal_game \
  --dataset '<test UUID>' --files-root '/absolute/private/audit-exports'
npm run --silent audit:cleanup -- apply --schema royal_audit --game-schema royal_game \
  --dataset '<test UUID>' --files-root '/absolute/private/audit-exports' --sha256 '<SHA-256 из проверенного плана>'
```

`plan` читает в отдельной транзакции без записи. В результате перечислены таблицы, точное число строк, контрольные суммы содержимого, управляемые файлы и блокирующие условия. Любой рабочий UUID отклоняется. План с открытыми операциями, активными заданиями, пересекающимися ссылками, неизвестной зависимостью или превышенным лимитом нельзя применить. Верхняя граница инвентаризации составляет 20 000 строк на таблицу и 64 МиБ содержимого на таблицу. Проверка файлов и источников также имеет собственные пределы.

`apply` повторно вычисляет план по тому же UUID. Он сравнивает SHA-256, проверяет зависимости и под короткими блокировками PostgreSQL удаляет только строки тестового аудита. Перед удалением дополнительно сверяются метаданные зарегистрированных файлов. В той же транзакции создаётся отдельный рабочий UUID со своим снимком остатков. При занятом источнике возвращается `source-busy`. Проверка исходных данных сравнивает кошельки, сохранённые операции и обязательства, границы журналов и каждую проводку, которая была связана с тестовым набором. Для транзакции действует предел 30 секунд на PostgreSQL 17. Оригиналы остаются в канонических источниках.

После коммита удаляются только зарегистрированные файлы из проверенного плана. Состояние `files-pending` означает, что переключение уже зафиксировано, а файловая часть ждёт завершения. Повторите `apply` с тем же SHA-256 и каталогом. Повтор возвращает тот же рабочий UUID и продолжает файловую часть по журналу. Закрытый тестовый UUID, контрольная сумма и итог хранятся в журнале.

Рабочие ссылки на проводки начинают записываться с новой контрольной точки. Для записи технических попыток игровому процессу задаётся `ROYAL_AUDIT_LIVE_DATASET_ID` с новым UUID и `ROYAL_AUDIT_SCHEMA`. Настройка `ROYAL_AUDIT_TEST_DATASET_ID` используется отдельно, одновременно можно указать один UUID. Разрешения операторов выдаются для нового набора и нужных источников. ## Приёмка на целевом стенде

Единая финансовая копия из одной точки PostgreSQL включает схему `royal_audit`, когда она существует. Для восстановления сохраняются отпечатки данных, контрольные суммы определений триггеров и список их активных источников. Закрытый набор с отключённым триггером также требует схему аудита. Старые копии продолжают проверяться по своему формату.

В результате `latest` поле `restore` показывает последнюю попытку для конкретного архива. Для приёмки сверяются SHA-256 копии и признаки `ok=true`, `status=complete`, `audit_verified=true`, `cleanup_verified=true`. Успех записывается после завершения временного контейнера и удаления его рабочей папки. При новой проверке `last_success_at` остаётся исторической отметкой. Текущая попытка при этом имеет собственный статус.

Владельцем объектов аудита для этой процедуры служит `finance_schema_owner`. Допускаются группа `royal_audit_reader` без LOGIN и служебные роли `royal_audit_recorder`, `royal_audit_worker`, `royal_audit_risk`. Именованные рецензенты используют LOGIN вида `royal_audit_reviewer_anna`. После префикса допускаются строчные латинские буквы, цифры и одиночные подчёркивания между частями имени. Полное имя ограничено 63 символами. В изолированной базе роли создаются без паролей для проверки архивных прав. Пароли и членство операторов выдаются отдельно. Неизвестный владелец или получатель прав блокирует подготовку копии.

Локальная репетиция использует два временных PostgreSQL 17 без TCP. Укажите каталог клиентских и серверных программ PostgreSQL 17 в `ROYAL_TEST_PG_BIN`.

```sh
python3 deployment/finance/test-audit-backup.py
```

Перед включением на целевом стенде проверьте штатное восстановление согласованной копии вместе с доступом ролей, продолжением и остановкой захвата. Измеренные пределы экспорта и задержек фиксируются отдельно для этого стенда. [Процедура копирования](../../deployment/finance/operations.py) · [Проверка нагрузки](load.md)
