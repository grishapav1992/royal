# Нагрузочная проверка аудита

OPS-03 запускает временную PostgreSQL на loopback и создаёт синтетические аккаунты. Параметры подключения выдаёт тестовый раннер. Команда удаляет принадлежащую ей базу и папку выгрузок после завершения. Результат выводится в JSON. [Сценарий](../../scripts/audit-load.ts) · [Автоматическая проверка](../../server-tests/paid-activity-audit-load.test.ts)

```sh
node --import tsx scripts/audit-load.ts
node --import tsx --test server-tests/paid-activity-audit-load.test.ts
```

## Нагрузка

По умолчанию четыре параллельных исполнителя выполняют по восемь сценариев. У каждого есть пара для PvP и отдельный игрок для казино. Пара подключается к обычному `LobbyRoom` через Colyseus с проверкой сессии. Стенд расставляет игроков по местам до замера. Вызов и принятие удерживают две ставки. Отмена до начала возвращает обе ставки. Сдача после начала матча рассчитывает выплату и комиссию. На отдельном аккаунте одновременно выполняется Plinko через публичный маршрут кошелька с обычной проверкой сессии, привязкой аккаунта и обработкой прогресса.

Первая фаза выполняется до старта набора аудита. В фазах с аудитом работают транзакционный захват проводок, штатные наблюдатели HTTP и WebSocket и фоновая запись реплеев выбранного PvP-сценария. Две разные учётные записи операторов по очереди запускают CSV истории игрока и сводку. В обычном сценарии история содержит 80 заранее подготовленных проводок, которые выгружаются по одной строке на страницу. Скрипт отдельно считает пересечение вызовов кошелька с окнами отчётов. После осушения очереди сверяются записи набора и подтверждается закрытие соединения наблюдателя.

Параметры `--workers`, `--rounds` и `--seed` ограничены диапазонами 1–8, 2–16 и 8–40 соответственно. На каждой фазе сверяются точные суммы проводок, остатки, квитанции команд, оба удержания матча, состояние банка и комиссия. Ответы HTTP и WebSocket сверяются с балансом и ID исходной проводки. В фазах с аудитом проверяются решения `accepted` и `replayed` и ссылка на баланс каждой попытки. После выплаты победитель повторяет одну из ранних команд. Ответ должен указывать на выплату в том же кошельке. Для каждого сыгранного матча стенд заново читает сохранённый реплей, проверяет его движком и сверяет ссылки на оба удержания и выплату. Операции повторов измеряются отдельно. Для p95 берётся ближайший порядковый ранг по всем успешным вызовам фазы. Ошибки и число выполненных вызовов выводятся рядом.

Кошелёк и комнаты работают в отдельном процессе и получают только переменные подключения к временной PostgreSQL. Поле `transport` отмечает HTTP-измерение казино и WebSocket-измерение PvP. Подключение и расстановка игроков проходят до замера вызова, принятия и расчёта матча. `nodeCpuMicros` относится к процессу раннера. Счётчики PostgreSQL относятся к тестовой базе.

## Диагностика ответа PvP

Добавьте `--pvp-timing` к той же команде для сопоставления ответа клиента с этапами на сервере. Режим включается только в изолированном процессе стенда. Он собирает первые `create`, `accept`, `cancel` и `resign` каждой фазы и забирает пакет замеров после её завершения. Повторы с тем же ID остаются в отдельной метрике `retry`. Идентификаторы запросов служат для сопоставления и отсутствуют в итоговом JSON.

В `pvpTiming` есть выборки по каждому действию и по двум группам, удержанию и расчёту. Для p95 и самой медленной команды показаны этапы одного и того же запроса. `completed` считает успешные команды, `traced` считает начатые записи в процессе кошелька, `matched` считает полные сопоставления с обеими транзакциями. При отсутствующем замере этапы запроса могут быть пустыми. `firstReportOverlap` означает пересечение с интервалом выполнения первого отчёта. Активный SQL проверяется отдельно.

`beforeStoreMs` включает постановку в очередь комнаты, ожидание и предварительные проверки до вызова хранилища. `commandTransaction` и `syncTransaction` показывают время до входа в тело транзакции, работу в ней и возврат из неё. До входа PostgreSQL-клиент получает соединение, выполняет `BEGIN` и запрашивает advisory lock. Этот интервал измеряется целиком. Чтобы подтвердить причину ожидания, требуется отдельное наблюдение PostgreSQL. В `roomMs` входит обработка до завершения метода комнаты. Общая метрика p95 по клиенту продолжает определять результат прогона.

Провели четыре диагностических прогона на `b628ac76` с включённым режимом замеров и 250 000 старыми проводками. В каждой из трёх фаз прогона сопоставлены все 96 команд. ## Проверка пределов отчётов

`--scale-history` добавляет 20 001 синтетическую проводку пополнения в исходный журнал после открытия тестового набора. Ссылки захватывает штатный триггер. В отчётной истории одного игрока 10 000 строк. Проверяются принадлежность строк, порядок, точные суммы и расчётный и записанный остатки во всём CSV.

После CSV второй оператор формирует узкую сводку по настоящим тестовым операциям. Отдельные роли затем запрашивают сводку по 20 000 и по всем 20 001 синтетическим проводкам. Штатная проверка должна вернуть `scan-limit` и сохранить причину в журнале с нулём строк и байтов. Отдельный запрос по 20 000 проводкам должен дать точный итог 2 000 000 минимальных единиц. Роли используют предел временных файлов PostgreSQL 32 МиБ.

```sh
node --import tsx scripts/audit-load.ts --scale-history --workers 4 --rounds 8 --seed 40
```

Свою границу приёмки можно передать через `--stake-p95-budget-ms`, `--settlement-p95-budget-ms` и `--reader-stop-budget-ms`. Эти параметры сравнивают p95 ставки и расчёта при работающем аудите и время остановки SQL после отмены. JSON содержит результат каждого заданного сравнения. Команда завершается кодом 1 при превышении. В режиме `--pilot-gate` порог роста 10% применяется отдельно к удержанию PvP, расчёту PvP и полной HTTP-операции казино. Проверяется пересечение всех трёх видов вызовов с первым отчётом. Измерения на локальной базе сохраняют `capacityConfirmed=false`.

Поле `budget.readerStopTarget` указывает сценарий сравнения. `primary-active-query` измеряет остановку активного запроса, заблокированного на основной базе. `standby-active-query` измеряет остановку активного запроса на физической реплике после записи первой строки CSV. При выборе реплики JSON также сохраняет независимые замеры на основной базе и при отмене ожидания WAL. Время от сигнала отмены до ответа команды и время до исчезновения серверного процесса сохраняются отдельно.

## Отмена и объём

Отдельная проверка временно удерживает блокировку исходной таблицы. После появления файла `.part` и подтверждения ожидания SQL в `pg_stat_activity` выгрузка получает сигнал отмены. Скрипт сверяет статус `cancelled` в журнале, отсутствие частичного и конечного файла отменённой выгрузки и исчезновение читающего соединения из PostgreSQL. Время ответа об отмене и время исчезновения соединения измеряются отдельно.

При проверке активной реплики вторая страница ждёт тестовую блокировку после выполнения проекции. До сигнала отмены проверяются первая строка во временном CSV и точный процесс PostgreSQL. Блокировка остаётся занятой до исчезновения этого процесса. У тестовой функции отключён `lock_timeout`, поэтому сценарий проверяет поведение при штатном `statement_timeout` в 5 секунд. Журнал должен записать нулевые счётчики, файл должен исчезнуть, а новый тяжёлый отчёт получает `report-busy` до подтверждения освобождения слота. Тестовая функция устанавливается после замеров игровой нагрузки.

До включения проверки сокета в диагностическом прогоне на PostgreSQL 17.10 ответ об отмене активного CSV вернулся через 2,245 мс. Процесс реплики исчез через 5 006,248 мс, а при отмене ожидания WAL через 1,087 мс. Переданный для проверки лимит в 1 000 мс был отклонён по замеру активного запроса.

На том же Mac повторили тот же сценарий с проверкой закрытия сокета в читающей сессии. Процесс реплики завершился через 84,057 мс, процесс на основной базе через 98,326 мс. Лимит в 1 000 мс прошёл по замеру активной реплики. Денежные результаты совпали, ошибок захвата не было. Результат сохраняет `capacityConfirmed=false`. [Настройка читающей сессии](access.md)

Размеры измеряются после подготовки схемы аудита и после работы, включая подготовку истории для отчётов. `pg_database_size` показывает объём файлов базы, а `pg_total_relation_size` включает данные, индексы и TOAST. Средний и максимальный размеры ссылки на проводку и тела наблюдения попытки вычисляются через `pg_column_size`. Они описывают записи этого сценария. Физический рост включает заполнение страниц таблиц и индексов и журнал заданий.

## Границы измерения

Стойкость к повтору, отмена и измерения проверены для ограниченного локального набора. Фазы идут последовательно и используют один экземпляр PostgreSQL с раздельными аккаунтами. В расширенном сценарии синтетическая история появляется во второй фазе, поэтому разница между фазами включает изменение объёма данных и состояние кеша. Значение `capacityConfirmed=false` отражает охват стенда. Оценка целевой ёмкости требует прогона на целевой инфраструктуре с ожидаемым объёмом истории, параллелизмом и профилем запросов.

## Отчёт за 30 дней при накопленной истории

`--retained-history-rows` добавляет от 1 до 1 000 000 старых синтетических пополнений в ту же базу и набор аудита. Параметр требует `--mixed-history --pilot-gate`. ## Порог p95 для пилота с одним активным отчётом

`--pilot-gate` включает расширенную историю и контрольную фазу с включённым аудитом без отчётов. По умолчанию контроль идёт первым. Флаг `--control-after-reports` меняет порядок фаз, чтобы можно было проверить влияние прогрева и порядка запуска. В каждой фазе тот же поток выполняется на свежих парах аккаунтов. Узкая сводка ограничена заранее подготовленным аккаунтом и в обоих порядках читает ровно две проводки на каждый раунд `--seed`. Запись попыток каждой фазы завершается до начала следующей. В JSON сохраняется `pilotGate.phaseOrder`. Порог p95 и проверка отсутствия ошибок одинаковы в обоих порядках.

Сценарий запускает по одному CSV на 10 000 строк, узкую сводку, сводку на 20 000 проводок и запрос сверх предела. У каждого отчёта отдельная роль. Начало нагрузки ждёт активного SQL первого отчёта. С `--summary-first` первым выполняется сводка по 20 000 проводкам, в обычном порядке первым идёт CSV. Журнал подтверждает последовательность, а JSON показывает фактическое число ставок и расчётов, совпавших по времени с каждым отчётом.

Оба p95 могут вырасти максимум на 10%. Требуется одинаковое число операций без ошибок и тайм-аутов. Порог оценивается для выбранного порядка при пересечении первого отчёта со ставками и расчётами. Код 1 означает невыполненное условие сценария. Результат до включения аудита выводится отдельно от пилотного сравнения.

```sh
node --import tsx scripts/audit-load.ts --pilot-gate --workers 4 --rounds 8 --seed 40
node --import tsx scripts/audit-load.ts --pilot-gate --workers 4 --rounds 8 --seed 40 --summary-first
```

`--report-process` переносит все четыре отчёта в отдельный процесс Node.js на той же машине. Процесс запущен до обеих фаз и не получает задач во время контроля. Учётные данные временных ролей передаются по IPC, а объёмы, порядок отчётов и пределы остаются прежними. Для сравнения топологий каждый из двух вызовов выше повторяется с этим флагом.

Эта схема испытана для одной известной физической реплики с синтетическими данными. Её функции допуска закрыты по умолчанию, а контроллер запускается только в тестовом окружении. Нагрузочная приёмка на отдельном целевом стенде и сетевой контроль прямых SQL-подключений к реплике остаются открытыми.

## Почему сводка достигала тайм-аута на 8×16

Вложенный `auto_explain` на временной PostgreSQL 17.10 показал два плана для одной сводки по 20 000 проводкам. При 4×8 PostgreSQL искал запись по `demo_ledger_pkey`. При 8×16 он выбирал `demo_ledger_time` по аккаунту и времени и проверял ID после чтения. В тестовом интервале записи имели одинаковое время. На каждый из 20 000 поисков приходилось в среднем 5 000 отброшенных записей, всего около 100 млн проверок и 2 560 416 попаданий в буферы журнала вместо 60 000.

Общий SQL отчётов теперь сначала находит запись по уникальному ID проводки, затем сверяет аккаунт, операцию и время с захваченной ссылкой. Несовпадение любого поля по-прежнему даёт `source-unavailable`. В повторном диагностическом прогоне обе нагрузки выполнили по 20 000 поисков через `demo_ledger_pkey`, с 60 000 попаданий в буферы журнала. На 8×16 вложенная сводка заняла 198,743 мс вместо 6 029,082 мс и вернула прежний точный итог. Для записи завершённого плана диагностика временно давала одному запросу 30 секунд в отдельном запуске. В штатной команде предел SQL остаётся 5 секунд, а порог p95 кошелька оценивается отдельно.
