# Доступ к аудиту платной активности

У оператора свой PostgreSQL LOGIN. Администратор создаёт отдельную группу NOLOGIN и выдаёт операторам членство в ней. Имя группы передаётся в установщик доступа. Используйте учётные записи без владения объектами, привилегированных атрибутов, других членств и прямых прав на таблицы. Задавайте пароли через действующий механизм управления секретами. При отзыве доступа удалите разрешения оператора из таблицы ACL и членство в группе. Перед повторным использованием имени проверьте, что старых разрешений для него нет.

```sql
CREATE ROLE royal_audit_reader NOLOGIN;
GRANT royal_audit_reader TO named_operator;
```

Установщик выдаёт группе USAGE на схему аудита и EXECUTE на ограниченные функции. Миграция привязана к выбранному имени группы. Роли установки, управления разрешениями и очистки обслуживаются отдельно от операторов отчётности.

Администратор добавляет разрешения в `audit_report_acl` отдельно для каждой пары `dataset_id` и `source_namespace`. Запись ссылается на зарегистрированный источник набора. Функции используют PostgreSQL `SESSION_USER` как имя оператора. Переход через `SET ROLE` сохраняет эту идентичность.

```sql
INSERT INTO royal_audit.audit_report_acl(operator_name,dataset_id,source_namespace)
VALUES ('named_operator', '<dataset UUID>', 'royal_game.demo_ledger');
ALTER ROLE named_operator SET temp_file_limit = '64MB';
```

После миграций источников запустите установку от служебной учётной записи с `ROYAL_AUDIT_CLEANUP_DB_URL_FILE`. Команда создаёт таблицы в заранее подготовленной схеме аудита, устанавливает журнал очистки, права группы и функции для всех видов отчётов. Для платёжного контура на той же базе добавьте `--payments-schema royal_payments`. Повтор с теми же схемами и группой применяет те же миграции.

```sh
npm run --silent audit:cleanup -- install --schema royal_audit --game-schema royal_game \
  --reader-role royal_audit_reader
```

Служебная учётная запись должна владеть объектами аудита и иметь право читать нужные исходные таблицы. Операторы получают только групповой доступ к ограниченным функциям и индивидуальные разрешения на выбранные источники. [Модуль доступа](../../server/audit/report-access.ts) · [Установка и очистка](cleanup.md)

## Журнал выгрузок

- `audit_report_begin(dataset, kind, filters)` фиксирует оператора, набор, тип, фильтры и время начала. Для `player` обязательны `accountId`, `fromMs`, `toMs`. Для `summary` аккаунт необязателен. Можно указать `category`, `gameId`, `modeId`, `asset`, `contour`. Период ограничен 31 сутками.
- Для `detail` и сверки одной проводки указываются `source` и строковый `postingId`. Сверка периода журналирует `source`, `fromMs`, `toMs` и необязательный `accountId`. Для `replay` указывается `replayId`. Каждый отчёт повторно проверяет права после фиксации задания.
- На одного оператора разрешена одна активная выгрузка. Через пять минут её идентификатор теряет силу. Следующий разрешённый запуск этого оператора отмечает просроченную запись как `expired`.
- `audit_report_finish(job, outcome, row_count, byte_count, reason)` фиксирует результат своей активной выгрузки. Успех требует указать количество строк и байтов. Для ошибки и отмены принимаются фиксированные коды причин. Запись результата и счётчиков отражает сообщение клиента выгрузки.
- Запуск и завершение выполняются отдельными короткими транзакциями. Чтение отчёта использует отдельную транзакцию. Запись о начале сохраняется при ошибке или отмене чтения.

Страницы доступны после коммита задания. Каждая страница заново проверяет права оператора и срок задания. В активном наборе чтение идёт по мере коммитов. Поздно завершившаяся операция с ключом до уже прочитанной страницы может войти только в следующую выгрузку. Для фиксированного состава проводок используйте закрытый набор.

## История игрока

Перед запуском задайте `ROYAL_AUDIT_DB_URL_FILE` как путь к файлу с PostgreSQL URL оператора. Для подключения по TLS задайте `ROYAL_AUDIT_PGSSLMODE=verify-full` и при необходимости `ROYAL_AUDIT_PGSSLROOTCERT`. Команда использует явное операторское подключение. В примере период задан в UTC.

```sh
npm run audit -- player --schema royal_audit --dataset '<dataset UUID>' --account '<account ID>' \
  --from 2026-11-07T00:00:00Z --to 2026-11-08T00:00:00Z --output ./postings.csv
```

Нижняя граница периода включена, верхняя исключена. Дополнительные фильтры задаются через `--category`, `--game`, `--mode`, `--asset`, `--contour`. В консоль выводятся ID задания и объём файла. CSV сохраняет исходный порядок по времени, источнику и числовому ID строки, точные целые денежные единицы и один ряд на проводку. Комиссии без отдельной проводки раскрываются в проверке банка. Ожидаемый баланс вычисляется от контрольной точки для первой проводки или от сохранённого остатка соседней проводки. Колонка `expected_balance_basis` различает эти случаи и отсутствие данных. CSV показывает финансовую проекцию, а проверка правил и доказательств остаётся отдельной операцией.

Лимиты пилота составляют 31 день, 10 000 строк, 20 000 просмотренных ссылок, 16 МиБ CSV, 60 секунд на чтение и запись и 5 секунд на запрос. Роль должна иметь ограничение временных файлов PostgreSQL не выше 64 МиБ. Существующий путь сохраняется, временный файл создаётся с правами владельца в той же папке, финальное имя появляется после полного завершения записи. Отмена закрывает соединение чтения и удаляет временный файл. Если файловая система после публикации не дала удалить временное имя, команда сообщает его в `cleanupPending`. При потере связи с журналом после публикации команда сообщает `journal-unavailable` с ID задания. Самостоятельное чтение через SQL использует ограниченную функцию с активным заданием. Показатели завершения передаёт клиент.

Строки с потенциальными формулами экранируются при создании файла. Для точного отображения длинных чисел импортируйте денежные колонки в таблицу как текст. Пробелы покрытия, в том числе отсутствие исходной строки, отражаются отдельным статусом. Массовая выгрузка всех игроков требует отдельного нагрузочного допуска.

## Сводка по периоду

```sh
npm run audit -- summary --schema royal_audit --dataset '<dataset UUID>' \
  --from 2026-11-07T00:00:00Z --to 2026-11-08T00:00:00Z
```

Сводка выводит JSON с моментом чтения `asOf`, списком разрешённых источников, количеством просмотренных ссылок и отдельными счётчиками пробелов. Строки группируются по контуру, активу, масштабу, категории и виду движения. Суммы и счётчики проводок сохраняются точными десятичными строками. Положительная сумма подтверждённого вывода берётся из расхода резерва в проводке `paid:` и относится к времени этой проводки. Платёжное зеркало остаётся свидетельством доставки.

Комиссия PvP и общего пула показывается отдельной строкой без дополнительной проводки. Для периода она относится к первой зафиксированной строке расчёта всего банка в наборе. При фильтре по аккаунту общая комиссия остаётся нераспределённой, что отражает `feesExcludedForAccount`. Сводка ограничена 20 000 авторизованных ссылок до применения фильтров по виду игры и активу. Превышение лимита завершает задание с `scan-limit`. Пилот использует те же ограничения времени и PostgreSQL, что история игрока.

## Детали операции и реплей

Возьмите `source` и `posting_id` из истории игрока. Если известен исходный ID, вместо `--posting` используйте ровно один селектор `--operation`, `--round`, `--match` или `--ticket`. Укажите полный источник проводок. Селекторы раунда, матча и билета работают с игровым `demo_ledger` и проверяют соответствие исходной сущности. Селектор операции работает и с разрешённым платёжным источником.

```sh
npm run --silent audit -- detail --schema royal_audit --dataset '<dataset UUID>' \
  --source royal_game.demo_ledger --posting '<posting_id>'
npm run --silent audit -- detail --schema royal_audit --dataset '<dataset UUID>' \
  --source royal_game.demo_ledger --match '<match UUID>'
npm run --silent audit -- replay --schema royal_audit --dataset '<dataset UUID>' \
  --replay '<replay UUID>' --output ./match.json
```

Если для ID операции или раунда найдены проводки нескольких аккаунтов, команда возвращает `ambiguous-account` без списка аккаунтов. Повторите запрос с известным `--account`. Селектор матча по умолчанию показывает подтверждённые проводки обоих участников. Флаг `--account` ограничивает разбор одним участником. Журнал сохраняет исходный селектор, а ответ отдельно показывает найденную ссылку на проводку. Если раунд или билет были открыты до начала аудита, поиск может найти завершение по контрольной точке. Предшествующие набору проводки в ответ не включаются. Поиск ограничен 128 исходными ссылками, запросами или аккаунтами на этапе разрешения. При превышении предела возвращается `scan-limit`.

Детализация показывает точные суммы, связанные проводки в выбранном источнике, сохранённую операцию, доступный исход, события и попытки. У сформированного ответа баланс и его подтверждённый снимок указаны отдельно. Недоступный исход или отсутствующий снимок обозначены явно. Лимиты одной детализации составляют 128 проводок, до 64 событий и до 64 попыток, не более 256 КиБ данных.

При выгрузке реплея права проверяются для набора, исходной игровой сущности и ссылок на проводки. В JSON сохраняется тестовая маркировка. Результат команды показывает состояние покрытия и факт проверки совместимым движком. Отсутствующая, неполная, повреждённая и неподдерживаемая запись имеют отдельные статусы. Запись файла атомарна, предел составляет 12 МиБ. [Локальный просмотрщик](replay-package.md)

## Денежная сверка

```sh
npm run --silent audit -- reconcile --schema royal_audit --dataset '<dataset UUID>' \
  --source royal_game.demo_ledger --posting '<posting_id>' --wait

npm run --silent audit -- reconcile --schema royal_audit --dataset '<dataset UUID>' \
  --source royal_game.demo_ledger --from '2026-11-07T12:00:00+03:00' --to '2026-11-07T12:05:00+03:00' \
  --account '<account_id>' --wait
```

Команда ставит сверку в очередь. Без `--wait` она сразу возвращает текущее состояние запроса. С этим флагом она ждёт до 40 секунд, после чего готовый результат можно забрать тем же запросом. Повтор использует ту же запись очереди. `--refresh` заново ставит завершённую сверку в очередь. Одновременно в очереди и обработке допускается до 64 запросов. Если очередь занята другим запуском, команда возвращает `queue-busy`.

Результат разделяет `financialErrors`, `coverage` и `signals`. В каждом финансовом выводе есть код правила и ссылки. `finishedAt` показывает время завершения расчёта. `replayIds` содержит связанные сохранённые пакеты, для выгрузки которых отдельно проверяются разрешения. Если сверка использовала второй денежный источник, при чтении результата проверяется допуск и к нему.

Для периода задаётся один денежный источник. Без `--account` выборка включает всех игроков этого источника. Начальная граница включается, конечная исключается. Длина окна ограничена 31 днём, число проводок для полного разбора ограничено 16, результат ограничен 1 МиБ. При `scan-limit` известно, что найдено минимум 17 проводок. При `byte-limit` итог превысил размер. Оба статуса возвращаются без частичных находок. Для повторной проверки можно сузить окно или указать игрока.

Выборка и правила сверки используют один снимок PostgreSQL. В ответе есть `asOfMs`, время начала и остановки захвата и число проверенных проводок. Выход за границы захвата отражается в `coverage`. Связанные расчёты, подтверждающие проводки и сигналы могут относиться к моменту за пределами заданного окна. Поля `anchors` и `sources` связывают находку с выбранными проводками и доказательствами. Денежные ошибки включают ID доступных реплеев, сигнал включает ключ для просмотра ручного разбора.

Для расчёта служебная учётная запись использует URL из `ROYAL_AUDIT_WORKER_DB_URL_FILE`. Ей нужны SELECT на используемые исходные и аудиторские таблицы, USAGE на соответствующие схемы, UPDATE на очередь сверок и предел временных файлов до 64 МиБ. Оператор отчётности вызывает только ограниченные функции. Расчёт выполняется на отдельном подключении с дедлайном 35 секунд и пределом три секунды на SQL-запрос. После истечения двухминутной аренды запрос снова доступен обработчику.

```sh
npm run --silent audit:reconcile-worker -- --schema royal_audit --game-schema royal_game --watch
```

Без `--watch` процесс обрабатывает одно доступное задание. Если подключены платежи, укажите `--payments-schema` с именем канонической схемы.
