# Контрольная точка тестового аудита

`AuditDatasets` подготавливает отдельную схему аудита. Источники конфигурируются из серверных имён схем, на одном подключении PostgreSQL. Игровой журнал, отложенный остаток провайдера и, при указании схемы платежей, первичный платёжный журнал регистрируются отдельно. Платёжное зеркало исключено из списка источников проводок. Платёжный охват при отсутствии подключения ограничен явно выбранными источниками.

`startTest()` создаёт серверный UUID и метку `test`. Под коротким `SHARE ROW EXCLUSIVE NOWAIT` на исходных таблицах фиксируются остатки и открытые обязательства. Если писатель уже удерживает несовместимую блокировку, PostgreSQL возвращает `55P03` и транзакция откатывает попытку целиком. Повтор старта при том же активном наборе возвращает его ID. Режим работы кошелька не зависит от обычного чтения отчёта. Захват блокировок и создание триггеров выполняет только оператор с разрешениями на исходные таблицы.

`audit_posting_refs` связывает набор с исходными строками. Триггер фиксирует связь в транзакции проводки, поэтому откат удаляет обе записи, а выделение ID до переключения не определяет принадлежность. История до контрольной точки отсутствует в наборе. Успешный расчёт старого матча связывается с записью открытого обязательства. Выделенный после старта ID и время проводки служат для порядка, а не для определения членства в наборе. Отложенный остаток хранится отдельным компонентом. Ёмкость кошелька под выплату не подменяет основную сумму удержания.

`AuditEvidence.record` сохраняет проверенные события, попытки и метаданные воспроизведения. Если вызывающий код использует тот же экземпляр базы внутри денежной транзакции, откат затрагивает и событие. Совпадающий повтор возвращает `replayed`, изменение сохранённого содержимого с тем же ключом отклоняется. Технический ответ можно записывать отдельно. Для базы источника потребуются отдельные привилегии на запись аудита, которые будут задаваться при вводе.

`sealTest(id)` закрывает набор для новых записей. Операция проверяет метку и синхронизируется с уже выполняющимися писателями. Повтор закрытия безопасен. Триггеры остаются установленными, но вне активного набора не создают ссылок. Удаление записей и переключение на рабочий режим относятся к задачам OPS-01 и OPS-02. Эти API не включаются при обычном старте игрового приложения.

Для уже открытого тестового набора отдельно включается наблюдение транспорта. Оно записывает технические ответы после денежной операции и помечает обнаруженные потери наблюдений. [Запись попыток](transport-attempts.md)

## Чтение и связь с игровым расчётом

`AuditPostingReader.read(datasetId, source)` проверяет членство исходной строки в наборе и читает её с серверных источников. Проводки казино, PvP, общих пулов и платежей связываются по ключам операций и сущностей. Старое обязательство отмечается через снимок на старте. Недоступный источник, неизвестный вид и отсутствие записи в выбранном наборе различаются. Читатель работает с одной проводкой и предназначен для разбора. Ограниченная потоковая выборка и команды оператора относятся к CLI-02 и CLI-03.

Сессии казино дают связь с автоматическим расчётом без искусственного клиентского запроса. PvP сохраняет частичную связь через банк при отсутствующей игровой версии. Для общего пула зачисление раскрывается до отдельных билетов. Старые билеты имеют порядковый номер, а точное время решения о приёме требует отдельного наблюдения. Резолвер платежей возвращает исходную проводку, а платёжная проекция остаётся свидетельством доставки.

## Денежная сверка

| Правило | Источник и граница проверки |
| --- | --- |
| R-01–R-03 | Начальный остаток, исходные проводки, сформированный ответ и отпечаток принятой команды сравниваются отдельно. [Сверка остатков и повторов](check-balances.md) |
| R-04 | Принятые условия, сохранённая версия расчёта и фактические проводки раунда. Платный вход в бонус и бесплатное продолжение различаются. Если состояние многошагового раунда на момент закрытия набора не зафиксировано, проверка показывает пробел. [Сверка казино](../../server/audit/check-casino.ts) |
| R-05 | Удержания и обе стороны банка матча, выплата или возвраты, единственная комиссия. Ёмкость под выплату сверяется отдельно от удержанной ставки. [Сверка PvP](../../server/audit/check-pvp.ts) |
| R-06 | Банк, комиссия, распределение и возвраты по версии общего пула. Время принятия требует отдельного серверного свидетельства. [Сверка пула](../../server/audit/check-tote.ts) |
| R-07 | Резерв, расход резерва и возврат по исходным строкам платежей. Связь противоположных корректировок требует отдельного поля источника. [Сверка платежей](payment-postings.md) |

## Изолированная проверка

```sh
node --test server-tests/paid-activity-audit-{contract,fixtures}.test.mjs
node --import tsx --test server-tests/paid-activity-audit-{check-balances,ws-attempts}.test.ts
node --import tsx scripts/database-test.ts --import tsx --test --test-concurrency=1 \
  server-tests/paid-activity-audit-{datasets,evidence,attempts,http-attempts,casino,pvp,tote,payments}.test.ts \
  server-tests/paid-activity-audit-check-{repeats,casino,pvp,tote}.test.ts
```

Тесты покрывают оба контура, старый резерв PvP, доставку платёжного зеркала после границы, занятый срез, откат, заранее выделенный меньший ID, закрытие набора и смену набора. Для фикстур ожидаемые финансовые результаты и поведенческие метки записаны отдельно от входных событий.
