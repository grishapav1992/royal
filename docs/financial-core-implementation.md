# Реализация финансового ядра Рояля

Первый этап реализован как отдельный серверный модуль для симулированных средств. Он поддерживает пополнение, переводы, резервирование ставок, расчёт игр и резервирование вывода. Все денежные изменения проходят через PostgreSQL с двойной записью и устойчивыми ключами повторов.

Актив называется `USDT_SIM`. Настоящие USDT, TRON, приватные ключи, покупка криптовалюты и отправка денег пока не подключены. Демокошелёк и текущие игры используют прежний механизм. Финансовый API предназначен для доверенного локального оператора симуляции, а не для браузера игрока.

Ядро также развёрнуто на тестовом VPS в отдельном Compose-проекте: два API, закрытый HAProxy и постоянный PostgreSQL. Управление сервером описано в [инструкции развёртывания](../deployment/finance/README.md), перенос на независимые ресурсы в [архитектуре отказоустойчивости](../deployment/finance/HIGH-AVAILABILITY.md). Контейнеры API читают рабочие секреты из файлов и не получают административный пароль базы.

## Проверка без настройки базы

```sh
npm run finance:demo
npm run test:finance
npm run check:finance
```

Демонстрация и тесты запускают отдельный настоящий PostgreSQL на свободном локальном порту, создают временную базу и ограниченную роль приложения. После завершения процессы останавливаются, временная база удаляется. Переменные подключения к существующим базам не используются. Бинарные файлы PostgreSQL поставляются dev-зависимостью `embedded-postgres`; Docker и системная установка PostgreSQL для этих команд не нужны.

Демонстрация выполняет следующий сценарий на симулированных средствах:

1. Оператор вносит 1000 USDT_SIM капитала.
2. Алиса вносит 100 и переводит Бобу 20.
3. Боб резервирует ставку 5 с покрытием максимальной выплаты 10 и получает выплату 10, включая возврат ставки.
4. Боб резервирует вывод 10, операция становится неопределённой, затем симулятор подтверждает её завершение.
5. Итог: у Алисы 80, у Боба 15, резервов пользователей нет. Активы сервиса составляют 1090, обязательства игрокам 95, свободный бюджет оператора 995. Сверка возвращает `ok: true`.

Суммы в ответах представлены строками минимальных единиц: `15000000` означает 15 USDT_SIM. Масштаб равен 6. Преобразование десятичного пользовательского ввода выполняет `parseUsdt`; оно не округляет лишние знаки.

## Гарантии проведения

Рабочая роль `royal_finance_runtime` имеет чтение таблиц и вызов двух публичных процедур. Она не имеет прямых INSERT, UPDATE, DELETE или TRUNCATE, доступа к внутренней процедуре проводок и права создавать объекты финансовой схемы. Приложение при запуске проверяет эти условия и отказывается работать с владельцем базы, суперпользователем, правом репликации, обхода RLS или другими избыточными правами.

Процедура денежной операции проверяет разрешённые поля, точные суммы и тип инициатора, блокирует совпадающий ключ повтора, затем блокирует затронутые счета в стабильном порядке. Проводки, баланс, состояние операции, сохранённый ответ и outbox фиксируются атомарно. Взаимоблокировка или ошибка сериализации допускают ограниченный повтор с тем же ключом. Неясная ошибка подключения требует проверки операции либо повтора исходного запроса с тем же ключом.

Проверки базы запрещают отрицательные расходуемые остатки, превышение предельной суммы, несбалансированный журнал и несоответствие кэша баланса проводкам. Проведённую историю нельзя обновить или удалить обычной командой, а в журнал из уже завершённой транзакции нельзя дописать новые проводки. Администратор базы с правом менять схему может обойти эту защиту; независимый внешний аудит относится к следующим этапам.

Повтор ключа с теми же параметрами возвращает исходный ответ. С другим телом или видом операции он возвращает конфликт. Повтор источника пополнения с другим ключом не зачисляет деньги повторно. ID вывода и раунда также уникальны.

Outbox пока хранит события для будущих обработчиков. Отправляющий worker, доставка событий и независимый подписывающий контур не реализованы.

## Игры и вывод

Резерв ставки переводит средства из доступного баланса пользователя в игровой резерв. Одновременно максимальная выплата резервируется из свободного бюджета оператора. Игра не начинается без этого покрытия. Выплата больше согласованного максимума отклоняется. Расчёт или отмена раунда освобождают покрытие один раз.

Игровой симулятор принимает доверенную тестовую сумму выигрыша. Это не проверка настоящего результата игры: перед подключением к платным играм потребуется независимый серверный расчёт, фиксированные правила и доказательство источника результата.

Резерв вывода включает сумму и комиссию. Отмена допустима только из `reserved` и возвращает весь резерв. Из `unknown` отмена запрещена: тайм-аут не доказывает отсутствие выплаты. Подтверждение симулятора погашает резерв один раз и учитывает комиссию отдельно. Настоящие доказательства отправки, срок действия транзакции, попытки подписи и сетевые расходы будут добавлены в адаптере сети.

Поддерживаются только назначения вида `simulation:recipient`. Настоящий криптоадрес отклоняется. В этой версии нет функции создания реальных кошельков.

## Отдельный HTTP сервис

Для ручной работы используйте отдельную локальную PostgreSQL базу, например `royal_finance_sim`. Миграцию выполняет владелец схемы с правом первоначального создания роли; сервис подключается другим логином.

Переменные окружения:

```dotenv
FINANCE_MODE=simulation
FINANCE_MIGRATION_DATABASE_URL=postgresql://schema_owner:password@127.0.0.1:5432/royal_finance_sim
FINANCE_DATABASE_URL=postgresql://royal_finance_app:password@127.0.0.1:5432/royal_finance_sim
FINANCE_SANDBOX_TOKEN=replace_with_64_hex_characters
FINANCE_PORT=2570
```

Значения `password` и `replace_with_64_hex_characters` являются заполнителями. Секреты храните в локальном `.env` или окружении. Сервису не передаётся миграционный пароль в качестве рабочего подключения.

```sh
npm run finance:migrate
```

После миграции администратор создаёт отдельный логин и назначает ему рабочую роль. Например, в psql:

```sql
CREATE ROLE royal_finance_app LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE INHERIT;
GRANT royal_finance_runtime TO royal_finance_app;
GRANT CONNECT ON DATABASE royal_finance_sim TO royal_finance_app;
```

Пароль этого логина задаётся отдельно командой psql `\password royal_finance_app`. При назначении уже существующего логина с NOINHERIT нужно проверить наследование членства, а не только изменить атрибут логина.

```sh
npm run finance:dev
npm run build:finance
```

При обычном запуске сервис слушает `127.0.0.1:2570`. В закрытой Docker-сети разрешён явный `FINANCE_BIND_HOST=0.0.0.0` вместе с `FINANCE_NETWORK_SCOPE=private-docker`; compose-файл не публикует порт на хосте. Для запуска обязательны режим `simulation`, рабочее подключение и случайный токен из 32 байт в hex. При `NODE_ENV=production` запуск запрещён. Сборка создаёт `dist-server/finance.js`; основной игровой сервер автоматически его не запускает.

Подключение также поддерживает файлы `FINANCE_DATABASE_URL_FILE` и `FINANCE_MIGRATION_DATABASE_URL_FILE` либо отдельные `FINANCE_DB_HOST`, `FINANCE_DB_PORT`, `FINANCE_DB_NAME`, `FINANCE_DB_USER`, `FINANCE_DB_PASSWORD_FILE`. Для внешней базы задаётся `FINANCE_DB_TLS=verify-full`, при необходимости `FINANCE_DB_CA_FILE`; проверяются сертификат и имя сервера. TLS-параметры в URL запрещены. `FINANCE_DB_POOL_MAX` ограничивает пул значением 1..50.

На VPS общий вход `http://finance-gateway:2570` распределяет запросы между двумя API. Ключи повторов и денежное состояние сохраняются в общей базе. `/healthz` возвращает 503 при недоступной базе, standby или подключении только для чтения. Проверки через разные API и после остановки одного процесса пройдены; независимый сервер и переключение самой PostgreSQL ещё не развёрнуты.

## Команды HTTP API

Все `/sandbox/*` маршруты требуют `Authorization: Bearer <токен>`. Денежные POST-запросы также требуют заголовок `Idempotency-Key` с UUID. Запросы с Origin отклоняются, CORS не включён. Это не заменяет пользовательскую аутентификацию: сервисный токен даёт оператору право управлять всеми симулированными пользователями и не должен попадать в браузер или публичный прокси.

| Маршрут | Действие |
| --- | --- |
| `POST /sandbox/users` | Создать финансового пользователя, тело `{ "userId": "alice" }` |
| `POST /sandbox/operations` | Выполнить команду, тело `{ "actor": "alice", "kind": "transfer", "body": { "recipientId": "bob", "amountUnits": "20000000" } }` |
| `GET /sandbox/wallets/:userId` | Доступный баланс и резервы |
| `POST /sandbox/wallets/:userId/deposit-address` | Постоянный тестовый адрес, тело `{ "network": "tron-sim-v1" }` |
| `GET /sandbox/wallets/:userId/history` | Последние 50 проводок пользователя |
| `GET /sandbox/operations/:actor/:key` | Исходный результат операции по её ключу |
| `GET /sandbox/reconciliation` | Сверка журнала, балансов и резервов |
| `GET /healthz` | Готовность базы к записи, название сервиса и режим симуляции без токена |

| Команда | Инициатор | Поля body |
| --- | --- | --- |
| `simulate_deposit` | `simulator` | `userId`, `eventId`, `amountUnits` |
| `simulate_capital` | `simulator` | `amountUnits` |
| `transfer` | ID отправителя | `recipientId`, `amountUnits` |
| `reserve_withdrawal` | ID владельца | `withdrawalId`, `destination`, `amountUnits`, `feeUnits` |
| `cancel_withdrawal` | ID владельца | `withdrawalId` |
| `simulate_withdrawal_unknown` | `simulator` | `withdrawalId` |
| `simulate_withdrawal_confirm` | `simulator` | `withdrawalId` |
| `reserve_game` | ID игрока | `roundId`, `stakeUnits`, `maxPayoutUnits` |
| `settle_game` | `game-simulator` | `roundId`, `payoutUnits` |
| `cancel_game` | `game-simulator` | `roundId` |

ID событий, выводов и раундов имеют формат UUID. Все суммы являются строками минимальных единиц, ноль разрешён только для комиссии и выплаты проигранного раунда. Выплата включает возврат ставки, если он предусмотрен результатом симулированной игры.

## Поступления из симулятора сети

Добавлен отдельный наблюдатель, использующий два лабораторных источника и собственный логин `finance_ingest`. Он обрабатывает только подтверждённые согласованные блоки сети `tron-sim-v1` и токен `simulation:usdt-test-v1`. Проверяются контракт, получатель, успешное исполнение, точность, сумма и внутренние перемещения. Событие, проводки, outbox и курсор фиксируются атомарно. Повтор сканирования и перезапуск базы не начисляют деньги второй раз. Изменение уже подтверждённого блока постоянно останавливает поток.

Схема версии 2 добавляет четыре таблицы к прежним девяти. Миграция сохраняет прежние денежные записи. Наблюдатель не получает сервисный токен, права перевода или вывода. Адреса имеют префикс `simulation:`, реальными кошельками они не являются. [Формат, правила и проверка на VPS](../deployment/finance/DEPOSITS.md).

## Следующие этапы

До реальных средств остаются адаптер TRON с проверкой поступлений, управление депозитными адресами, изолированная подпись, независимые одобрения, реальные попытки отправки и восстановление их неопределённых результатов. Отдельно нужны финансовая аутентификация и второй фактор, ограничения пользователей, внешний аудит и оценка применимых требований.

Для симулятора уже настроены часовые копии, ежедневное полное восстановление, мониторинг на VPS и зашифрованная внешняя копия на Mac. Полное восстановление проверено из обоих мест хранения. Для боевого режима нужны круглосуточное независимое хранение и контроль, архивирование WAL, отказоустойчивый кластер и испытания переключения. [Инструкция эксплуатации](../deployment/finance/OPERATIONS.md).

Для высокой нагрузки текущую проверку баланса через полный SUM проводок нужно измерить и оптимизировать, сохранив инварианты. Общие счета оператора также являются точками конкуренции. Первая версия предназначена для проверки корректности, а не для неограниченного потока ставок.

Следующий технический этап: RPC-адаптер тестовой сети TRON с явно выбранным тестовым контрактом и отдельным контуром тестовых ключей. Лабораторный этап уже проверяет финальность, ложные токены, повторы событий и восстановление сканирования; проверка настоящих receipt, полноты RPC-выборки и сверка активов в сети ещё нужны до подключения USDT.
