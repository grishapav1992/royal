# Распределение игровых комнат

Изменение подготовлено и проверяется локально. Рабочий сервер автоматически не переключается.

`compose.websocket.yaml` добавляет к `compose.yaml` три процесса игровых комнат и закрытый Valkey. Процесс `game` остаётся единственным входом для API, подбора комнат и фоновых обработчиков платежей. Комнаты распределяются между `game` и `worker-1`/`worker-2`/`worker-3`. Caddy направляет WebSocket по адресу владельца комнаты; переподключение возвращается к тому же процессу.

Без дополнительного Compose-файла остаётся один процесс. Вручную запущенный кластер требует `REDIS_URL`, `PUBLIC_ORIGIN`, уникальный `LOBBY_WORKER_ID`. Главный процесс использует ID `main` и `LOBBY_WORKER_ONLY=false`; остальные используют `LOBBY_WORKER_ONLY=true`. Два процесса с одинаковым ID не запускаются.

## Ограничение HTTP API

Перед JSON-парсером и проверкой сессии `/api` ограничивается по IP: 1800 запросов за минуту и 180 за 10 секунд. Платёжные уведомления NOWPayments и подписанные callbacks Casino Api Pro используют отдельный бюджет: 6000 за минуту и 600 за 10 секунд. Проверка подписей остаётся обязательной. Внутренние подписанные события `/internal/payments/events` не расходуют бюджет браузера, чтобы начисления продолжались при его превышении. `/healthz` и статические файлы также не расходуют этот бюджет.

USDT, Nile Play и криптокошелёк после подтверждения владельца используют общий бюджет аккаунта: 240 запросов за минуту. Внутри него предусмотрены отдельные лимиты: чтение 120, игровые действия 180, пополнение/котировка/подключение 20, вывод 5, проверка ранее отправленной операции 30. Криптокошелёк дополнительно сохраняет прежний общий предел 60 запросов за минуту. Демокошелёк сохраняет 240 запросов за минуту. Вход ограничен 80 попытками на IP и 10 на адрес почты за 15 минут. Некорректное тело и повтор операции тоже расходуют бюджет. Лимит не меняет идентификаторы финансовых операций и не отменяет защиту от повторного начисления.

При наличии `HTTP_RATE_LIMIT_REDIS_URL` или `REDIS_URL` счётчики общие для всех API-процессов с одинаковым `PUBLIC_ORIGIN`. Инкремент и срок жизни выполняются атомарно. При отказе Redis API возвращает `503`, локального сброса лимитов нет. Без Redis допускается один API-процесс с ограниченным хранилищем в памяти; запуск нескольких API-копий требует общего Redis. Пределы по IP можно менять четырьмя `HTTP_RATE_LIMIT_*` параметрами из `.env.example`, учитывая игроков за одним NAT. Превышение возвращает `429`, короткий JSON и `Retry-After`, без бана аккаунта.

IPv6-адреса одной подсети `/64` расходуют общий бюджет, включая ограничения входа и платёжных уведомлений. IPv4-адреса остаются независимыми; запись IPv4-mapped IPv6 использует тот же бюджет, что соответствующий IPv4. Некорректное значение forwarded-адреса использует адрес соединения и не создаёт новый счётчик.

Адрес клиента принимается из forwarded-заголовков только через локальные или частные proxy peers. Публичный порт игрового процесса должен оставаться закрытым за Caddy; Caddy должен перезаписывать forwarded-заголовки. Эти HTTP-лимиты не заменяют ограничение WebSocket-пакетов и защиту сетевого канала.

## Границы и проверки

По умолчанию каждый процесс допускает 10 комнат по 30 игроков и 330 сокетов, включая переходные подключения. Четыре процесса дают потолок 1200 мест. После отказа одного процесса остаётся только 900 мест. Запас соединений 330 не увеличивает число мест в комнатах. Для 1000 игроков с сохранением допуска при отказе потребуется отдельно проверенная конфигурация с дополнительной вместимостью. Это ограничение допуска, а не подтверждение скорости при 1200 игроках. Реальную нагрузку нужно измерить на целевом сервере с движением, взаимодействиями, переподключениями и остальными работающими сервисами.

Очередь выбора процесса ограничена 128 запросами. Проверка авторизации имеет отдельный предел параллельных запросов. Новые входы при перегрузке получают 429 или 503. Уже зарезервированные входы и переподключения имеют ограниченную очередь с приоритетом. Медленный получатель с очередью отправки больше 256 КиБ отключается отдельно.

Рабочие процессы используют общий PostgreSQL и отдельный небольшой пул: по умолчанию `LOBBY_WORKER_PGPOOL_MAX=6` и `LOBBY_WORKER_AUTH_CONCURRENCY=4`. Нужен запас соединений для главного процесса, Миры, финансовых сервисов и обслуживания базы. Пулы не создают соединение на каждого игрока.

Имя, персонаж, опьянение, выход и решения охраны передаются между процессами через Valkey. Получатель перечитывает актуальное состояние аккаунта из PostgreSQL. Потеря общей связи прекращает допуск и закрывает игровые подключения, после чего процесс завершается с ошибкой и перезапускается.

Общий lease аккаунта в PostgreSQL запрещает одновременное нахождение одного аккаунта в разных комнатах. Продление выполняется пакетами каждые 10 секунд. Переподключение имеет 20 секунд; при аварийной остановке процесса освобождение аккаунта может занять до 45 секунд. Истечение lease останавливает действия и удаляет аватар из симуляции. Обычный выход освобождает lease сразу. Комната и её временные взаимодействия при остановке владельца не переносятся в другой процесс.

## Проверка перед переключением

1. Прочитать `SERVER.md`, сохранить исходники, отметить предыдущий образ и сохранить текущий `game_data`. Сохранить серверный `.env` и домены.
2. Проверить совмещённую конфигурацию: `docker compose -p royal -f compose.yaml -f compose.override.yaml -f compose.websocket.yaml config --quiet`. На рабочем сервере сохранить точный существующий список Compose-файлов и добавить overlay последним. Проверять развёрнутую конфигурацию в приватном файле, без вывода секретов. Workers наследуют исходный `compose.yaml`, поэтому отдельно сравнить их PostgreSQL environment, secret targets и сети с актуальными настройками main; нужные overrides перенести явно.
3. Выполнить сборку и целевые тесты. `npm run test:cluster` использует временный локальный PostgreSQL и локальный `redis-server`; Valkey можно указать через `ROYAL_REDIS_SERVER_BINARY`.
4. Проверить запас CPU, памяти и соединений PostgreSQL до запуска дополнительных процессов. На небольшом VPS четыре процесса делят существующие ядра.
5. До переключения выполнить длительный тест и отдельные проверки отказов на изолированном стенде. Нагрузочный генератор выключает автоматическое переподключение, поэтому его PASS не подтверждает recovery. Подготовить полный production-образ с Redis-зависимостями на базе свежего рабочего выпуска; дополнение пакетов стенда не заменяет production-образ. Переключать только игровые процессы и Caddy контролируемо, без сборки на занятом VPS. После переключения проверить готовность процессов, адреса владельцев, выход, охрану и повторный вход.

При откате остановить дополнительные процессы и Valkey, вернуть прежний список Compose-файлов и отмеченный образ. Новая таблица `lobby_account_leases` может остаться в базе. Не удалять рабочие данные и не заменять серверный `.env` локальным.

## Стоимость симуляции и локальный нагрузочный тест

Движение сохраняет три шага проверки столкновений, но записывает итоговые координаты в сетевое состояние один раз за входной шаг. Охрана, Мира и фоновые гости избегают лишних обходов и записей; повторяющиеся маршруты охраны используют кэш на 128 точных пар координат. Изменение препятствий сбрасывает кэш, а вызывающий код получает отдельную копию маршрута.

Время сервера передаётся раз в секунду. Между обновлениями клиент отсчитывает время монотонными часами; переподключение сбрасывает привязку. Симуляция NPC остаётся 60 Гц, движение и отправка изменений состояния остаются 20 Гц. Формат сетевых координат сохранён.

После `npm run build` выполнить локальное сравнение:

```sh
npm run test:load:cluster -- --proxy-binary /absolute/path/caddy --clients 1000 --seconds 70 --60hz --output artifacts/websocket-simulation/load-local.json
```

Тест создаёт временные PostgreSQL и Valkey, четыре игровых процесса и четыре независимых генератора клиентов. Для Valkey вне PATH указать `ROYAL_REDIS_SERVER_BINARY`. Для нагрузки больше 100 клиентов обязателен локальный Caddy: путь передаётся через `--proxy-binary` или `ROYAL_CADDY_BINARY`. Запасной прокси на Node разрешён только для малых проверок; его работа в одном потоке может исказить большую нагрузку. Соединения разрешены только с локальным компьютером; `.env` не загружается, внешние сервисы выключены. Для сравнения предыдущего собранного сервера указать `--server-bundle /absolute/path/server-bundle.js`. Файл результата должен быть новым.

Генератор явно использует транспорт `ws` и сохраняет его название и версию Node в отчёте. Встроенный транспорт Node можно включить для диагностики через `--sdk-websocket native`. Аргумент `--resource-diagnostics` добавляет CPU и память локального Caddy, а на macOS также изменение общих счётчиков сжатия памяти и swap за время измерения. Эти счётчики относятся ко всему компьютеру. `--frame-diagnostics` предназначен для разбора входящих сообщений; его нужно выключать при сравнении скорости.

Каждый клиент отправляет 30 пакетов в секунду, по два шага движения в пакете. Входы идут постепенно, максимум 20 новых игроков в секунду. В отчёте сохраняются ошибки входа, распределение комнат, частота отправки, задержка подтверждения последовательности ввода, остаток после двух секунд ожидания, CPU, память и задержки обработки событий по процессам. Подтверждение последовательности включает очередь сервера, отправку состояния и декодирование клиентом; оно не измеряет чистую задержку сети и не доказывает применение каждого шага.

Критерии локального сравнения: не менее 90% целевой частоты отправки, p95 подтверждений не более 250 мс и p99 не более 500 мс в каждом генераторе, остаток не более 1%, отсутствие ошибок и сохранение всех соединений. Пределы можно задать аргументами `--min-rate-percent`, `--ack-p95-ms`, `--ack-p99-ms`, `--max-unacknowledged-percent`. Это условия данного теста. Режим по умолчанию `stress` отправляет ввод без браузерного окна ожидания. `--input-mode browser-window` воспроизводит пределы очереди и неподтверждённого ввода клиента; его таймер отправки остаётся 30 Гц, поэтому это не полный браузерный сценарий. Тест не воспроизводит массовые переподключения, взаимодействия и конкурирующие рабочие сервисы. Итоговую ёмкость необходимо проверять на целевом оборудовании.

## Отдельный стенд и генераторы (этап 4)

Для проверки 1000+ игроков игровой кластер и генераторы запускаются на разных машинах. Серверный runner создаёт временные PostgreSQL, Valkey, четыре игровых процесса и тестовый прокси. Генераторный runner создаёт только SDK-клиентов. У обоих адреса остаются `127.0.0.1`; соединение между машинами идёт через два SSH-туннеля. Работа SSH и прокси тоже влияет на задержки и должна учитываться при оценке оборудования.

На отдельной тестовой машине с собранным проектом и локальным Caddy:

```sh
npm run test:load:cluster -- --proxy-binary /absolute/path/caddy --clients 1000 --seconds 70 --frame-diagnostics --input-mode stress --stand-manifest /tmp/royal-load-stand/private.json --client-origin http://127.0.0.1:17100 --output artifacts/websocket-stand/server-new.json
```

Для Valkey вне PATH указать `ROYAL_REDIS_SERVER_BINARY`. Runner выводит `serverApiPort` и `serverControlPort` в сообщении `stand-ready`. Это случайные порты на тестовой машине. Внутри временного стенда API и комнаты рекламируют клиентский адрес `127.0.0.1:17100`, поэтому туннель должен сохранять именно этот локальный порт.

На машине генераторов скопировать приватный файл и открыть туннели. Заменить `TEST_USER@TEST_HOST`, `SERVER_API_PORT` и `SERVER_CONTROL_PORT` на данные отдельного стенда:

```sh
ROYAL_LOAD_CLIENT_DIR=$(mktemp -d /tmp/royal-load-client.XXXXXX)
scp TEST_USER@TEST_HOST:/tmp/royal-load-stand/private.json "$ROYAL_LOAD_CLIENT_DIR/stand.json"
chmod 600 "$ROYAL_LOAD_CLIENT_DIR/stand.json"
ssh -N -o BatchMode=yes -o ExitOnForwardFailure=yes -L 127.0.0.1:17100:127.0.0.1:SERVER_API_PORT -L 127.0.0.1:17101:127.0.0.1:SERVER_CONTROL_PORT TEST_USER@TEST_HOST
```

В другом терминале на машине генераторов, подставив путь к скопированному файлу:

```sh
npm run test:load:generators -- --manifest /tmp/royal-load-client.XXXXXX/stand.json --control-port 17101 --workers 4 --input-mode stress --output artifacts/websocket-stand/generators-new.json
```

Длительность измерения `--seconds` задаётся целым числом от 1 до 1800 секунд. Файл содержит только синтетические сессии временной базы и случайный ключ конкретного запуска. Он создаётся с правами `600`, действует `seconds + 600` секунд с момента создания (не более 40 минут) и удаляется серверным runner при завершении. Копию на машине генераторов после теста удалить отдельно. Не публиковать этот файл и не включать в артефакты. Рабочие `.env` и данные в сценарии не используются. Все файлы результатов должны быть новыми.

До создания SDK-клиентов генератор проверяет роль стенда, идентификатор запуска, срок действия, хэш серверной сборки и параметры нагрузки у контроллера и через `/__load-stand/status` на самом игровом API. Ошибочный API-туннель отвергается до передачи игровых cookies и подбора комнат. Затем клиенты подключаются постепенно, и общий барьер начинает измерение после сброса серверных метрик. Генератор устанавливает отдельный таймер до `expiresAt`; истечение срока прекращает работу и запускает очистку. Отключение генератора также прерывает ожидание; завершение процессов и ответ с результатом имеют ограниченные сроки.

`stress` и `browser-window` запускать отдельно с одинаковым режимом на сервере и генераторах. Если ограничение клиентской очереди снижает фактическую частоту ниже бюджета, результат остаётся `inconclusive-generator-rate`. Само сохранение подключений не подтверждает заданную нагрузку. Потеря временных отметок ACK или неполное покрытие серверной диагностики даёт `inconclusive-metrics`. При включённой диагностике итог также требует равенства числа отправленных и полученных пакетов ввода.

`--frame-diagnostics` измеряет реальные входящие сообщения до ограничителя, передачу обработчику, принятие шагов очередью, удаление через обработку или отмену, возраст очереди, задержку наблюдаемого `inputSeq`, скопление пакетов, буферы и коды закрытия. Счётчики сбрасываются общим барьером; перед остановкой снимается последний снимок. Периодические снимки передают только последнее окно, итоговый снимок сохраняет последние 300 окон. Удаление старых окон не сбрасывает общие счётчики, максимумы и гистограммы задержек за весь прогон. Примеры всплесков и отметки отдельных подключений имеют фиксированные пределы; превышение пределов видно в отчёте. Эти обёртки работают только в тестовом bootstrap; для сравнения скорости диагностику выключать.

Генератор сохраняет до 8192 измерений в выборке. После этого p95 и p99 являются оценками; `sampleCount` и `sampling` сохраняются в обоих отчётах. Общее число, максимум и среднее считаются по всем измерениям. Временные отметки ограничены 512 неподтверждёнными пакетами на клиента; их потеря не может дать успешный результат. Виртуальный модульный тест с меньшим пределом в 32 отметки проверяет 1800 секунд и 54 000 пакетов: хранилище остаётся ограниченным, а число отправленных, подтверждённых и оставшихся пакетов считается точно. Это проверка алгоритма, а не реальный 30-минутный нагрузочный прогон. Валидация отчёта допускает накопительные счётчики до 664 200 000; предел хранения выборок от этого не увеличивается.

Очередь отправки каждого собственного тестового WebSocket ограничена 256 КиБ и проверяется до и после отправки. Достижение предела один раз фиксирует `generator-buffer-limit` и пиковый размер, блокирует последующие отправки этому клиенту и закрывает его сокет через `terminate` или `close`. Блокировка сохраняется, даже если закрытие не завершилось; такой прогон не получает успешный результат. Одна отправка может пересечь порог до проверки после неё. Буферы Node и WebSocket не показывают все очереди ядра, сети и прокси. Сравнение хэшей имён машин также не доказывает различие физического оборудования.

Для проверки самой связки без большой нагрузки:

```sh
npm run test:load:stand:smoke -- --proxy-binary /absolute/path/caddy --output-dir artifacts/websocket-stand/smoke-new
```

Этот сценарий запускает два прогона по 8 клиентов, проверяет отдельные runners, оба адреса через перенаправленные TCP-порты, режимы ввода, Node/Caddy, доставку пакетов и очистку. Он работает на одной машине и явно сохраняет `capacity1000Proven: false`.

## Подготовка длительного прогона (этап 5)

Проверены 53 модульных сценария стенда, 13 сценариев защиты VPS и шесть сценариев остановки и проверки результата удалённого запуска. Последние проверки используют подставные процессы и ответы, а не рабочий сервер. Одноразовые скрипты в артефактах имеют фиксированный идентификатор попытки; перед повтором нужны новые имена и файлы. После ревью исправлены очистка при потерянном ответе SSH, наблюдение за завершением защитного процесса и отказ от успешного результата при неполных данных. ## Этап 7: приоритет рабочего приложения и предварительная сборка стенда

## Этап 8: фактический запас и защищённый запуск

[Свежие 45 секунд без тестовых игроков](../artifacts/websocket-capacity-stage-8/server-baseline.json): 2 CPU, 2972,66 МиБ RAM, свободно 1223,09-1425,42 МиБ; условие 1396 МиБ прошло только 8/45 окон. CPU достигал 100%, семь секунд подряд был >=95%. HTTP 9/9 успешны, игра и Caddy не перезапускались. Полный длительный прогон на этом фоне не запускается, пороги защиты сохраняются.

[Remote supervisor](../scripts/load-remote-stand.py) и [Mac runner](../scripts/run-remote-websocket-stage.mjs) используют один приватный план режима 600. Каждый этап получает новый RUN и собственный root/container. Перед запуском сверяются точные production ID/image/StartedAt, хеши helper/guard/готовых файлов, workload, порты и пути. Сначала запускается независимый host guard, затем контейнер с неизменным image ID, read-only rootfs, UID 1000 и только собственными временными монтированиями. Вся тестовая сеть остаётся на loopback; SDK работает на Mac через SSH. Manifest с nonce и токенами не попадает в stdout и удаляется после остановки. Отсутствие отчётов, потеря ответа start, смена ID, выход guard и незавершённая очистка не дают PASS.

Текущий supervisor ограничивает весь stand суммарно 0,5 CPU и 896 МиБ. Это бюджет защищённой малой проверки, а не ресурсный бюджет для доказательства скорости 1000 игроков. Локальные 500 клиентов потребляли около двух ядер суммарно на server-side и более 1000 МиБ как сумму отдельных пиков game/parent/Caddy, без баз. [Ресурсный расчёт](../artifacts/websocket-capacity-stage-8/resource-envelope.md) отделяет эти измерения от предварительного диапазона будущего стенда. После выделения ресурсов нужен отдельный согласованный бюджет большой нагрузки и новый baseline.

[Аудит перехода и отказов](../artifacts/websocket-capacity-stage-8/cluster-cutover-audit.md) описывает worker/main/Redis outage, потерю владельца комнаты, reconnect и новый вход после account lease. Старые комнаты не переносятся между владельцами. 1000+ и production recovery остаются незавершёнными до настоящего длительного прогона и отдельных проверок отказов.


Итог текущего шага: [38 regression checks](../artifacts/websocket-capacity-stage-8/phase-8-verification.json) прошли (27 supervisor, 11 Mac runner). Проверка отдельной Linux PostgreSQL с настоящими init/start/SELECT 1/cleanup прошла на точном рабочем image с лимитом 0,1 CPU, 384 МиБ и 64 PIDs. Три временных контейнера и каталога удалены; public health 200, ID/image/StartedAt/restarts игры и Caddy сохранены. Четыре игровых процесса на Linux и реальные SDK игроки в этом шаге не запускались.

Отмена теперь записывается вне writable mount стенда. Private lifecycle lock упорядочивает create/start/stop: задержанный supervisor не запустит CREATED-контейнер после подтверждённой остановки. Это проверено отдельными regression cases; root helper не объявляет большую нагрузку подтверждённой по одной успешной очистке.

### Повторяемый локальный запуск отдельного стенда

[Runner](../scripts/run-dedicated-websocket-stage.mjs) управляет уже подготовленным private plan на новом VPS, отдельными SSH carriers, четырьмя или другим заданным числом SDK workers, сбором артефактов и очисткой. Он сверяет точные machine/image/helper/plan и host key, допускает только свежий UUID и не останавливает чужой активный прогон. Каждый carrier проходит проверку control/API до открытия следующего; весь набор повторно проверяется до передачи тестовых cookies генераторам. Число carriers задаётся отдельно от SDK workers, от числа workers до 128.

```sh
node scripts/run-dedicated-websocket-stage.mjs --plan /private/path/stage.json --direct-interface en0
```

Локальный plan хранится в каталоге с правами 700, файл с правами 600. Поля: `protocol: 1`, точный `remotePlan` supervisor, `workers`, `localPorts: { api: [ports], control: port }`, свежий абсолютный `outputDir`, `knownHostsFile` и его `knownHostsSha256`. Remote private root, helper, plan и неизменный Linux image должны быть подготовлены заранее. Plan не содержит fixture токенов; они передаются через временный private файл и удаляются после теста.

Для `--direct-interface en0` runner использует `ProxyCommand=/usr/bin/nc -4 -n -b en0 -G10 %h %p`; OpenSSH сам добавляет shell `exec`. Дублирование `exec` при очищенном окружении воспроизведено и исправлено до запуска игроков. Общие маршруты и VPN не меняются. Без параметра интерфейса применяется обычный системный маршрут.

Ресурсный монитор работает до завершения owned контейнера. Успешный итог требует cgroup CPU/memory counters и временного покрытия полного интервала каждого игрового процесса, orchestrator и Caddy, без разрывов более трёх секунд. Для длительных тестов начало bounded metric tail восстанавливается консервативно из полной длительности epoch. Проверяется конечный вердикт guardian, удаление local/remote fixtures и остановка всех собственных process groups, включая дочерний `nc`, если SSH уже завершён. 26 локальных проверок runner прошли; это проверки инструмента, отдельные от нагрузочного результата.

Частота у каждого генератора составила 99,29%-99,39% цели, суммарно 17882,69 пакета/с. ACK p95 максимум 193,908 мс прошёл бюджет, ACK p99 максимум 1657,489 мс при бюджете 500 мс не прошёл; максимальный ACK 2191,625 мс. Все 600 подключений сохранены, ошибок нет, остаток после drain нулевой. Получены все 536577 входных кадров и обработаны все 1074166 шагов без limiter/cancel/diagnostic errors. Максимальная очередь движения составила 13 шагов, локальный возраст receive-to-inputSeq 212,65 мс; максимальный p99 event loop среди секундных окон игровых процессов 13,55 мс.

Последняя живая проба на 71 мс раньше конца полного metric window, этот хвост не покрыт CPU counters. Наблюдаемые пики всего стенда с подготовкой: 4,941 CPU и 1648,22 MiB. Первый запуск runner до этого остановился на локальном двойном `exec`, до remote start и создания игроков; его отдельный artifact сохранён и не считается нагрузочным прогоном.

### Прямой TLS-транспорт для отдельного стенда

Runner поддерживает явный режим `transport: "direct-tls"` на macOS. [Локальный прокси](../scripts/load-direct-tls-proxy.py) слушает только `127.0.0.1` и для каждого принятого локального TCP-соединения создаёт отдельный IPv4 TLS socket к `31.56.189.118:26443`. `IP_BOUND_IF=25` привязывает этот socket к `en0` до подключения. API и WebSocket проходят через эти отдельные соединения; SSH остаётся для управления, передачи приватного manifest и получения артефактов. VPN и общие маршруты не меняются. Один Python-процесс обслуживает локальный прокси, поэтому его CPU, память и задержка event loop также сохраняются в результате.

К обычным полям private plan добавляются:

- `transport: "direct-tls"` и `remotePlan.tlsGateway: { "port": 26443, "serverName": "royal-load.test" }`.
- `directTls.proxySha256`: SHA256 проверенного исходника локального прокси. Необязательный `directTls.pythonExecutable` задаёт абсолютный путь к Python; иначе используется настроенный локальный runtime.
- От одного до четырёх SDK workers и точные `localPorts: { "api": [17100, 17102, 17103, 17104], "control": 17101 }`. Четыре API aliases не означают четыре общих TLS carriers: каждое локальное TCP-соединение получает свой upstream socket.

Перед запуском нужно подготовить свежий UUID и private root, закрепить актуальные helper/proxy, machine/image/bundle/metadata и SSH host key. Public PEM передаётся только через проверенный SSH-канал; локальный прокси сверяет его SHA256, цепочку сертификата и имя `royal-load.test`. Private TLS key остаётся в закрытом каталоге тестового сервера с правами 600. Проверка control и всех API aliases с nonce manifest выполняется до передачи игровых cookies.

Дополнительный Caddy TLS gateway работает внутри того же контейнера и входит в общий cgroup-бюджет стенда. На публичном порту разрешены только `GET /__load-stand/status`, `POST /matchmake/joinOrCreate/lobby`, `POST /matchmake/joinById/ID`, `POST /matchmake/reconnect/ID` и WebSocket `GET /workers/OWNER/PROCESS/ROOM` для владельцев текущего профиля. Остальные маршруты получают 404. Control API и REST-маршруты входа и аккаунта через этот gateway не открываются; status требует ключ конкретного стенда.

Остановка включает exact owned container, local process groups, удаление local/remote manifest, TLS key/certificate/config/PID и временных generated assets. Локальному TLS-прокси даются отдельные 10 секунд после SIGTERM до принудительного завершения, чтобы закрыть потоки и записать summary. PASS дополнительно требует чистых counters прокси, нулевого остатка активных соединений и подтверждённого удаления TLS assets. Первоначальные 37 локальных проверок runner прошли; с исправлением graceful cleanup и классификацией TLS-отказов прошли 40 проверок. Это проверки инструмента, отдельные от реальной нагрузки.
