# HTTP, Mortal Kombat and Cosmic validation release

This release updates body-parser 2.3.0 to 2.4.0 and its required qs 6.16.0 to 6.16.1, rejects unnecessary compressed application bodies and sends a public combat projection with only the recipient's input acknowledgement. The approved Cosmic canonical-origin validator is included with its complete-round qualification. Probabilities, prices, accepted stakes, common wallet storage and host contracts remain unchanged. Only the test:rtp-gate package script gains the Cosmic verification suite; dependency metadata remains identical apart from the two reviewed lock entries.

Prepare from a clean source commit already pushed to main with the shared release tools and the verified current production source as base. Run release:verify before prepare.py. The preparer checks every built byte, canonical source differences, the precise two-package lock transition and the installed decoder package trees. A separate production dependency cache is updated only for those two packages. The compatible combat and Cosmic modules are published after the backend using the existing guarded independent module installer. Older clients retain compatible rendering and acknowledgements. Other module pointers, host contracts and backend programs remain unchanged. The payment and reconciliation programs keep their verified existing bytes only after checking every transitive source input against production. Their freshly generated build files are recorded for comparison and are not included in the overlay.

Source paths come from the exact application commit's Git tree. The preparer excludes untracked local files, including ignored bytecode produced by tests. Generated or unobservable source paths are rejected again by the server before publication. A clean Git status alone does not establish that every file under a source directory belongs to the committed application.

A publisher repair may reuse the exact existing application artifact and candidate image. Pass `--helpers-commit <full-main-commit>` to the reviewed preparer while the application checkout remains clean at its original prepared commit. The preparer fetches origin and verifies that both commits belong to main. It reads only the seven fixed helper paths from Git, never from a dirty checkout. The separate helpers-source.json contains the raw commit and four Git tree objects; the server verifies the complete hash path from the pinned publisher commit to every installed helper blob. Recomputed file hashes cannot substitute helpers from another revision. Application source, runtime files, module packages, production baseline and the canonical release manifest stay identical. Record the application and publisher commits separately. The `install` operation reuses a retained build-result and publishes the application and modules under one uninterrupted set of three deployment locks, after fresh baseline, backup, candidate and disk checks. Do not run another build merely to update deployment tools.

The installer retains the three shared deployment locks and checks the complete current source, configuration hashes, all dependency bytes and symlink targets, running and prepared images, immutable client URLs, module state and other persistent service fingerprints. The image adds a single bounded overlay to the verified previous image. It does not install arbitrary packages on the server. All other dependency files and image settings must stay identical. The candidate repeats the delayed-gzip regression on its actual Node runtime without external networking or player data.

Before mutation, stream a source archive under a hard compressed-byte limit and create a bounded PostgreSQL game-wallet backup. Verify every archived source file, the dump format, previous index and rollback image tags. No full source staging copy is created. Preserve at least 5 GiB free and the explicit build margin before and after backup and build. The context uses hard links to the exact payload and is removed after verification. A retained complete backup is reverified instead of allocating another source or wallet archive; only the runtime overlay and build margins are reserved for that retry.

Immediately before switching, a temporary Compose one-off obtains the same PostgreSQL advisory transaction lock used by combat funding. The Python supervisor has one fixed 900 second acquisition budget covering Docker startup and draining; waiting output cannot renew it. The Node helper independently limits the actual SQL drain to 180 seconds while it waits for active combat and virtual PvP holds to reach zero. No source mutation is authorized before quiet and a fresh nonce confirmation. A single PostgreSQL session verifies its backend PID, transaction ID and exact advisory lock every two seconds. Fresh nonce challenges confirm that buffered events cannot authorize mutation. The lock has a hard 600 second deadline starting only at quiet, each critical command has a 420 second limit, and a missing confirmation fails within ten seconds. The acquisition budget does not extend these held-lock deadlines. Publication capacity is checked before draining, before source mutation and throughout critical commands. Only owned client process groups are terminated on failure. Explicit COMMIT acknowledgement and a successful client exit are required; post-commit Docker cleanup has a separate 120 second limit. Health checks run after release because application startup also uses the financial lock. A slow startup does not establish that later critical Docker commands can finish within their separate limits; inspect current daemon latency before retrying.

Terminating a Docker client does not cancel every operation already accepted by its daemon. An unknown outcome writes recovery-required.json and refuses an automatic second Compose command. Inspect the cancelled operation and all project game containers before explicitly invoking rollback. Matching observations over three seconds describe the observed state and do not prove daemon completion. Duplicate, renamed, foreign and transitioning game containers are refused. A known completed candidate can be repaired even when unhealthy. A rollback that must restart the game obtains a fresh financial gate; restoring source and metadata around the still-running original image avoids a needless restart. This protocol detects loss of the PostgreSQL lock and aborts further commands; it does not claim an uninterrupted funding fence after a database connection loss. No wallet dump is restored.

Rollback verifies the same wallet sources and combat contract, restores only this release's source delta and selects the verified previous image. It never restores wallet data from a dump. Recovery uses compare-and-swap to restore both previous active pointers while preserving every immutable version file. A retry may reuse only this exact package with the previous pointer; unrelated modules, edited files, deleted previous resources and later pointers are rejected. If the running image never switched, rollback avoids a needless restart. An unrelated later publication prevents rollback. Record exact commit, image and independent public checks in SERVER.md and push the deployment record before considering publication complete.

Review an orphan .pending-* module staging directory before retrying. The complete inventory guard refuses an unreviewed pending copy and retains it for inspection. Module publication temporarily uses umask 022 only inside the canonical installer so public resource directories stay traversable; private backup modes remain 0600.

The portable real PostgreSQL regression runs with `ROYAL_TEST_PYTHON=<python3> node --import tsx scripts/database-test.ts --import tsx --test deployment/releases/mk-security-20261026-v1/test-gate-bridge.ts`. It holds the real financial transaction beyond the previous 25 second limit and the 30 second idle timeout, verifies that a pending reservation has not charged either player, then confirms one debit and one refund after release. The optional cpu-priority-release-v3.py is a bounded operational helper for this already built release on the reviewed server. It changes only the Docker and containerd service cpu.weight files from 100 to 3023, checks each opened file identity, and restores both independently. It neither stops services nor changes application, financial-service or Compose settings. An independent watchdog observes the parent identity and a monotonic 1800 second deadline. Activation and restoration share an exclusive flock; the watchdog writes a terminal cancellation marker under that same lock before restoration. A release request between ready and activation, a finished watchdog, cancellation, or expiry refuses activation. Run test-cpu-priority-v3.py from this directory for eight isolated local scenarios, including cross-process ordering. After the operation explicitly release the lease and verify both original weights. This mechanism does not promise recovery after a host failure or a failure of both processes.
