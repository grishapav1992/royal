# Shared Nile wallet and PvP release

The release adds six 1v1 games with equal USDT Nile stakes and a 5% pot fee. Three card clients are independent modules. It preserves the current cabinet platform, GitHub worlds and CR vs. Leo audio. Separate demo/provider credits are hidden. The unrelated Neopolis prototype remains in source and the module inventory but is excluded from the published catalogue and Nile stakes.

Before this release the Nile service was already unhealthy. Its full source audit had grown to about 489,000 blocks, while reconciliation had a 120-second systemd deadline. The release preserves the complete audit, gives the play/reconciliation processes up to two CPUs, aligns the wrapper deadline to 300 seconds and systemd to six minutes, and timestamps source freshness after successful auditing. No tokens are minted or transferred by deployment. The casino reserve was zero at review; existing player funds remain owned by their players. Slots require separately funded test reserve.

`prepare.py` packages only a committed checkout built from its Git archive. It compares against a fresh, secret-free production source snapshot, retains existing immutable module versions and replaces reviewed external pointers with the corresponding new packages. `deploy.py` verifies production source, settings, service identities and pointers under both publication locks before backup, image builds and publication. Source and financial schema backups remain on the server; `.env`, signing keys and database contents are excluded from release payloads and Git.

Server commands are `check`, `build`, `finance`, then `game`. Source must already be pushed to `origin/main`. Financial publication runs the unmodified complete journal audit and requires a fresh successful reconciliation before the game switches. The host keeps all previous static URLs and read-only mounts. Other persistent services are checked for preservation. The new financial image inherits the existing isolated runtime and receives the current/legacy Go rule binaries from the reviewed game image.

`rollback` restores the previous game image, application source and module pointers only if no later publication changed them. It retains the upgraded financial service and its source, which remain compatible with the previous host. Active matches lose their room lease and refund. Never restore the pre-release database dump after new transactions. A production rollback also requires its matching source commit, push and deployment record under `AGENTS.md`.
