# Mortal Kombat with common virtual USDT

The user replaced Nile stakes with the existing freely topped-up virtual USDT on 24 October. The independent floor-2 module uses the host wallet and its standard top-up dialog. Existing CommonCombatWallet, virtual PvP journal and server simulation own funding, outcome and the 95% / 5% split. No financial network service is changed.

Prepare a clean committed source already included in main with the shared release tools, using the verified production commit from SERVER.md. prepare.py compares canonical source content against a fresh guarded snapshot and selects only exact reviewed outputs. The host/backend is installed first; modules.py then extends the host contract with Mortal Kombat and publishes compatible immutable packages under the shared locks. Old URLs and unrelated pointers remain intact.

Source, previous image and game-wallet backups are verified before installation. After any virtual wager is accepted, an old Nile backend cannot safely resume the virtual banks: preserve the database and use a compatible forward repair. Wallet history and accepted operations are never restored from a dump during rollback. Production verification reads public bytes; synthetic accounts and free top-ups are tested in an isolated database.

An existing PvP source archive may be reused only after its complete inventory exactly matches the current production snapshot. The installer creates a hard link on the same filesystem and verifies it again. Removing the other archive name leaves this release's recovery file intact. The disk budget then excludes only those already allocated source bytes, retains the 5 GiB reserve and build margin, and still creates a fresh game-wallet dump.

The constrained overlay never installs dependencies or copies the base image. Its storage budget includes the full uncompressed source size when a fresh archive is necessary, four copies of the exact runtime delta, a 64 MiB wallet dump limit and a separate 64 MiB margin. The dump stream aborts and removes its partial output before exceeding its allocation. Free space is checked again after the archive and image build; the 5 GiB reserve remains mandatory.

An interrupted build may reuse its existing recovery set only after complete source, HTML, dump-format and rollback-tag checks. It cannot rebuild an already built or published release. After stopping the task's stalled build, transfer the freshly verified payload to retire only its obsolete build context, then use `DOCKER_BUILDKIT=0` with the same generated Dockerfile when the BuildKit worker stalls. Run long publication jobs in a detached session with a private log and retain all three deployment locks.
