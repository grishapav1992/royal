# Финансовый кабинет владельца

Код кабинета и его проверенная сборка: `78cb1ccd53c64c08e2df836f9d14a9eb3926f1be`. Этот коммит входит в main. Сборка общего игрового клиента и внешние указатели игровых модулей не публикуются этим выпуском. Отдельный `dist-admin` содержит HTML, JS и CSS кабинета; backend, NOWPayments и Nile обновляются совместимо с общим кошельком и PvP.

`snapshot.py` читает отпечатки актуальных production-исходников, клиентских файлов, сервисов и конфигурации без значений секретов. `prepare.py` требует совпадения всех неизменяемых backend-входов с опубликованными исходниками. Если другой чат изменил сервер, сначала повторить snapshot и согласовать сборку. Запрещено обходить проверку или заменять боевую версию старым корневым checkout.

`deploy.py publish` работает под общими блокировками приложения и игровых модулей. Перед публикацией проверяет исходники и конфигурацию, сохраняет и проверяет архивы кода и согласованную копию трёх финансовых схем, помечает прежние образы. Три небольших образа наследуют проверенные действующие runtime, клиент игры сохраняется побайтно. Обновляются только payments, Nile и game; постоянные тома, настройки ресурсов, остальные переменные, домен, монтирования и службы проверяются на сохранность.

UUID владельца задан явно после поиска по указанной пользователем почте. Секреты не передаются в payload или Git. Изменение `.env` выполняется только на сервере с сохранением прежних значений и добавлением административного override к прежнему списку Compose. Финансовая роль игры не получает доступа к чужим схемам.

Если общий выпуск кошелька уже опубликовал кабинет, использовать `prepare-activation.py STAGE BEFORE OUTPUT SOURCE_COMMIT OWNER_ID`. Он проверяет исходники кабинета и все входы платёжной сборки по точному опубликованному коммиту. При таком варианте создаётся только образ payments, его внешние зависимости проверяются в настоящем runtime. Образы game и Nile сохраняются побайтно и пересоздаются только для передачи разрешения владельца. Старую сборку `78cb1cc` поверх новых правил игры не устанавливать. Первичный `prepare.py` принимает `STAGE BEFORE OUTPUT OWNER_ID`. Разрешение владельца передаётся в закрытом манифесте выпуска и серверной конфигурации, персональные идентификаторы в исходники не добавлять.

Проверка готовности требует healthy у трёх сервисов, доступности `/admin`, ответа 401 без сессии и совпадения прежней статики и внешних модулей. Финансовые данные и реальные операции не создаются для проверки выпуска. После проверки записать образы и результат в `deployment/SERVER.md` и отправить запись в main.

При откате не восстанавливать старую базу поверх новых операций. После появления `adjustment` сохранять совместимую версию финансового сервиса. Любой откат требует сохранения соответствующих исходников и записи в main по `AGENTS.md`.

Текущая подготовка следует `docs/release-process.md`: `STAGE` указывает на чистый committed checkout с результатом `release:prepare`, а не на новую копию проекта. `prepare-activation.py` выполняет `release:verify --github`, сверяет коммит и точные байты payments с единым манифестом и сохраняет его вместе с GitHub-квитанцией. Начальная архивная сборка описана выше только как история подготовки; поверх нового общего кошелька используется активация действующих образов.

При активации сверяются весь контракт кабинета и каждый фактический исходник payments из esbuild metadata. Остальные host-исходники и package scripts не входят в payload и не заменяются версиями из main. Изменения образов host и Nile запрещены проверкой точного image ID; после пересоздания проверяются прежняя программа, настройки, assets и публичные маршруты кабинета. Неопубликованные игры и оформление из общей сборки этим выпуском не устанавливаются.
