# Криптовалютный шлюз NOWPayments

В проект добавлены пополнения с конвертацией в USDT TRC-20, расчет и подтверждение вывода в выбранную криптовалюту, обработка подписанных уведомлений, сверка статусов и отдельный журнал реальных средств PostgreSQL. У каждого игрока свой учетный баланс, заявка пополнения и резерв вывода. Демомонеты, Nile и прежний прямой mainnet-кошелек не смешиваются с этим балансом.

Без аккаунта и ключей провайдера интеграция отключена. Окно «Криптокошелек» сообщает, что платежи еще не подключены. Демо- и тестовые игры продолжают работать. Фактический обмен и реальные выплаты нужно проверить после настройки аккаунта.

## Форма пополнения и QR-код

После обновления 11 октября 2026 вход называется «Пополнить баланс», создание платежа запускается кнопкой «Оплатить». Реквизиты и QR открываются в отдельном модальном окне поверх игры. Можно закрыть окно и вернуться к той же незавершенной оплате через «Продолжить оплату». При подтвержденном завершении показывается фактически зачисленная сумма USDT.

USDT выбран валютой отображения по умолчанию. Можно выбрать одну из 19 национальных валют для примерного эквивалента баланса и суммы, которую игрок указал в USDT. Это отображение по актуальному estimate NOWPayments, с временем расчета и минутным кешем. Отдельный серверный маршрут `/api/crypto-wallet/display-rate` требует авторизацию владельца и включенный шлюз. При недоступном или устаревшем курсе интерфейс показывает USDT. Смена валюты не меняет точный журнал USDT и не выполняет обмен средств. Ввод суммы и обязательства перед игроком остаются в USDT. Пополнения банковской картой этим обновлением не подключаются.

Форма видна вошедшему игроку уже до подключения провайдера. Пока шлюз отключен, создание платежа недоступно, адрес и действующий QR-код отсутствуют. После подключения игрок выбирает сумму в USDT, валюту и сеть и нажимает «Оплатить».

Реквизиты показывают фактическую сумму исходной монеты, валюту, сеть и адрес созданного платежа. QR формируется локально в браузере и содержит только этот адрес. Сумму, сеть и обязательный memo или тег игрок указывает и проверяет отдельно в своем кошельке. Для адреса и memo предусмотрены отдельные кнопки копирования.

Изменение выбора валюты в форме не изменяет реквизиты уже созданного платежа. Новый QR появляется только после получения нового адреса от провайдера. Реквизиты завершенного или истекшего платежа скрываются; при выходе или смене аккаунта адрес, memo и QR очищаются. До подключения настоящего аккаунта оплачиваемые адреса не создаются.

## Подключение аккаунта

### Проверка аккаунта 11 октября 2026

API Key и IPN Secret сохранены в существующем серверном `.env` через скрытый ввод. Прием, вывод и игры на реальном балансе остаются отключенными. Read-only запросы статуса, каталога, выбранных валют, минимума BTC -> USDT TRC-20 и оценки USDT TRC-20 -> BTC успешны. Доступны 357 включенных направлений, включая `usdttrc20`. Это проверка доступности расчетов, фактический обмен и зачисление еще не проверены.

Чтение Custody-баланса возвращает HTTP 403 `ENDPOINT_NOT_ALLOWED`: серверные IPv4 `45.192.12.242` и IPv6 `2a14:6e40:4:316::1` отсутствуют в разрешенных IP NOWPayments. Добавить оба адреса в Settings > Payments > IP addresses, затем повторить чтение баланса. API не подтвердил основной баланс аккаунта. Данные авторизации для автоматических выплат пока не настроены.

После добавления владельцем обоих IP повторное чтение `/v1/balance` отдельно через IPv4 и IPv6 вернуло HTTP 200 и пустой объект балансов. Ограничение доступа снято, основной актив этим ответом не подтвержден. В актуальном интерфейсе IP настраиваются через Settings > Whitelist > Whitelist IPs. Прием, вывод и игры на реальном балансе по-прежнему отключены.

Реальный ответ `merchant/coins` содержит `selectedCurrencies`. Обработка этого поля исправлена и включена в подготовленный образ выпуска `balance-checkout-20261010T214058Z`. Он будет использован при следующем запуске сервера перед активацией шлюза. Входящий memo для пополнения получает сервер от NOWPayments; обязательный memo для адреса вывода по-прежнему вводится пользователем и проверяется.

1. Создать аккаунт [NOWPayments](https://account.nowpayments.io/) и подтвердить с провайдером обслуживание проекта, юрисдикции и условия выплат игрокам.
2. Включить Custody, выбрать USDT TRC-20 (`usdttrc20`) единственным основным балансом для автоматического обмена входящих платежей. Дополнительные входящие остатки в исходной валюте не должны отключать этот обмен. Неправильный актив расчета сервер не зачисляет.
3. Включить нужные монеты и сети в Coin settings. Приложение пересекает подробный список поддерживаемых активов с валютами, разрешенными этому merchant-аккаунту. Поддержка направления и минимальная сумма дополнительно проверяются при создании операции.
4. Создать API-ключ и секрет IPN. Уведомления направляются на `PUBLIC_ORIGIN/api/crypto-wallet/ipn` по HTTPS.
5. Для выплат настроить доступ с IP сервера, правила разрешенных адресов и приложение 2FA. Доступность выплат на произвольные адреса игроков необходимо согласовать с провайдером: по умолчанию адреса ограничены whitelist.
6. Заполнить на сервере существующий `/opt/royal/.env` без изменения домена и прочих настроек. Ключи и секрет 2FA не помещать в чат или исходники.

```dotenv
NOWPAYMENTS_ENABLED=true
NOWPAYMENTS_API_KEY=
NOWPAYMENTS_IPN_SECRET=
NOWPAYMENTS_WITHDRAWALS_ENABLED=false
NOWPAYMENTS_GAMES_ENABLED=false
NOWPAYMENTS_EMAIL=
NOWPAYMENTS_PASSWORD=
NOWPAYMENTS_2FA_SECRET=
NOWPAYMENTS_CONVERSION_MARGIN_BPS=100
```

После проверенного пополнения включить `NOWPAYMENTS_WITHDRAWALS_ENABLED=true`, пополнить рабочий Custody-резерв и проверить небольшой вывод. Email, пароль и секрет приложения 2FA нужны для JWT и подтверждения существующей payout-партии. Ключ доступа API и IPN нужны уже для пополнений.

Средства для автоматических выплат должны находиться на балансе Custody. Основную казну можно хранить на отдельном кошельке, оставляя у провайдера рабочий резерв. Данная интеграция не выполняет автоматический вывод казны на внешний кошелек. Оператор должен поддерживать покрытие всех доступных балансов и незавершенных заявок. Расчеты в игровой БД сами по себе не являются переводами блокчейна.

При необходимости включить `NOWPAYMENTS_GAMES_ENABLED=true` для Royal Coins и рулетки. Каждая новая ставка дополнительно проверяет фактический баланс USDT Custody и покрытие максимального возможного выигрыша после всех обязательств перед игроками. Остальные автоматы сохраняют демобалансы. Полученный от провайдера устаревший или недоступный резерв не разрешает новую ставку.

## Суммы, комиссии и статусы

USDT хранится в целых единицах 0,000001. При пополнении зачисляется только подтвержденный `outcome_amount` в USDT TRC-20, после обмена и комиссий. Статусы `confirmed`, `partially_paid`, `failed`, `expired` сами по себе не зачисляют деньги. Одна заявка связывается с одним provider payment ID. Новый платеж требует нового адреса-заявки; повторное использование старого адреса не является поддерживаемым сценарием.

Расчет вывода действует две минуты. Он показывает сумму списания, примерный обмен, сетевую комиссию и минимально допустимую отправку. Дважды резервируется расчетная сетевая комиссия: сумма выплаты вычитается из фактически полученного после обмена актива. Оставшийся резерв сетевой комиссии сохраняется у сервиса; комиссия выше этого резерва покрывается оператором. Параметр `NOWPAYMENTS_CONVERSION_MARGIN_BPS` задает допуск ухудшения курса и комиссий относительно предварительного расчета, по умолчанию 1%. Он не является тарифом провайдера.

API провайдера ограничивает сумму выплаты шестью знаками после запятой даже для активов с большей точностью. Сервер округляет отправку вниз, никогда не вверх. Слишком маленькие суммы или ухудшение ниже подтвержденного минимума остаются на проверке. Пользователь видит расчет до подтверждения. Доступные направления и тарифы следует подтвердить небольшими реальными операциями: mocked-тесты не доказывают доступность маршрута в конкретном merchant-аккаунте.

При подтверждении вывода USDT перемещается из доступного баланса в резерв одной транзакцией PostgreSQL. Повторная отправка того же запроса и того же расчета не создает второй вывод. Обмен и создание payout выполняются максимум один раз; перед внешним запросом сохраняется маркер попытки. После потери ответа новую денежную операцию автоматически не создаем.

`finished` закрывает резерв. `failed` не возвращает деньги: NOWPayments может возобновить выплату. `rejected` возвращает резерв в доступные USDT только если предварительного обмена не было. При отклонении после обмена требуется возврат актива и ручная финансовая сверка, иначе возврат USDT создал бы непокрытое обязательство. Автоматические повторы подтверждения 2FA относятся к существующей партии, не создают новую выплату.

Уведомления проверяются через deep-sorted HMAC SHA-512 и постоянное по времени сравнение. Суммы из уведомления напрямую не зачисляются: сервер повторно читает состояние операции через API и проверяет order ID, валюту, сумму, адрес и memo. Обновление статусов известных операций выполняется каждые 15 секунд. Операции `review` не запускаются повторно автоматически.

## Восстановление потерянного ответа

Внутри рабочей среды с серверными credentials доступны команды. Скрипт не печатает ключи, пароль или секрет 2FA.

В production-образ включен `dist-server/crypto-reconcile.js`. В каталоге `/opt/royal` его можно запускать с текущей конфигурацией контейнера, например `docker compose exec game node dist-server/crypto-reconcile.js audit`. Команды ниже предназначены для среды разработки с установленным `tsx`.

```sh
node --env-file-if-exists=.env --import tsx scripts/crypto-reconcile.ts audit
node --env-file-if-exists=.env --import tsx scripts/crypto-reconcile.ts attach-payment PROVIDER_PAYMENT_ID
node --env-file-if-exists=.env --import tsx scripts/crypto-reconcile.ts attach-conversion OPERATION_UUID PROVIDER_CONVERSION_ID
node --env-file-if-exists=.env --import tsx scripts/crypto-reconcile.ts attach-payout PROVIDER_PAYOUT_ID
```

Перед `attach-conversion` оператор обязан сопоставить нужную операцию с кабинетом провайдера: его API не поддерживает наш уникальный идентификатор в запросе обмена. Скрипт дополнительно проверяет исходный актив, целевой актив, сумму, временное окно и уникальность provider ID. Если есть несколько одинаковых обменов и сопоставление неоднозначно, сначала разобраться с поддержкой. Эти команды прикрепляют уже существующий перевод, затем обычная сверка продолжает его. Ручной возврат после обмена или сомнительного исхода не выполняется этим скриптом.

## Публикация и проверка

Перед публикацией прочитать `deployment/SERVER.md`, сохранить исходники и отметить прежний образ, сохранить текущие тома и production `.env`. Обновляется только игровой сервис и его исходники; существующий финансовый тестовый контур не переключается на реальные деньги.

Проверки разработки:

```sh
npm run build
node --import tsx scripts/database-test.ts --import tsx --test server-tests/crypto-wallet.test.ts
node --import tsx scripts/database-test.ts node_modules/@playwright/test/cli.js test tests/crypto-wallet.spec.ts
```

Официальные форматы: [API NOWPayments](https://documenter.getpostman.com/view/7907941/2s93JusNJt), [описание endpoints](https://nowpayments.zendesk.com/hc/en-us/articles/21345824322717-API-and-endpoint-description), [IPN](https://nowpayments.zendesk.com/hc/en-us/articles/21395546303389-IPN-and-how-to-setup), [тарифы](https://nowpayments.io/pricing). Код не фиксирует рекламную комиссию как гарантированную стоимость.

## Mortal Kombat PvP escrow

Mortal Kombat uses the existing multi-user USDT custody wallet, rather than the legacy single-account mainnet demonstration wallet. Enable NOWPAYMENTS_COMBAT_ENABLED=true only together with the compatible game host, payment service and rules-2 game module. NOWPAYMENTS_GAMES_ENABLED remains false in the separate payment service: the game host simulates combat, and the payment service handles escrow only. No provider credentials are exposed to the game browser.

Only HMAC-authenticated internal combat/fund, combat/settle and combat/cancel calls can alter escrow. Public wallet endpoints expose neither winner selection nor cash settlement. Two stakes reserve atomically from existing balances; the winner receives 95% of the combined pot, with 5% recorded as the casino fee. Draw, cancelled funding and orphan matches refund without a fee. A delayed funding call cannot resurrect a cancelled match. Pending escrow is included in withdrawal availability, payout capacity, signed ledger notifications, reconciliation and the common wallet history.

The existing payment worker recovers expired matches without relying on a connected browser or game process. Configuration disables new stakes by default; terminal settlement and refunds remain available if combat activation is switched off. Local validation uses scripts/local-combat.ts under the isolated database test runner and a synthetic payment provider; it must never run against production data. See docs/combat-anticheat.md for the threat model and validation.
