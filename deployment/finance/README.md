# Финансовый контур на сервере

Рабочий сервер переведен на единую PostgreSQL 8 октября 2026. Порядок миграции, права, копирование и откат: [Единая база PostgreSQL](../POSTGRES.md). Исторические проверки SQLite ниже относятся к прежним выпускам. Фактическое переключение и результаты восстановления зафиксированы в [SERVER.md](../SERVER.md).

Royal Coins подключён к отдельному тестовому игровому журналу Nile. [Баланс, резерв выплат, привязка и восстановление](NILE-PLAY.md).

Финансовое ядро развёртывается отдельным Compose-проектом `royal-finance-sim`, с исходниками в `/opt/royal-finance`. Игровой проект остаётся в `/opt/royal`. Контур использует симулированные средства `USDT_SIM`; реальные криптокошельки и подпись ещё не подключены.

Четыре постоянных контейнера симулятора: два экземпляра `finance-api`, база `finance-db` и балансировщик `finance-gateway`. `finance-migrate` запускается при развёртывании и завершается с кодом 0 после миграции и настройки рабочего логина. Все рабочие серверные хранилища используют эту же PostgreSQL через закрытую сеть `finance_private`. Порты 2570 и 5432 не публикуются на хосте. Игровой сервер подключен к этой сети с ограниченным логином своей схемы.

Остановка одного API проверена: второй продолжает проводить операции, повтор запроса сохраняет один результат. Все контейнеры пока на одном VPS. Конфигурация подключения к внешней базе с проверкой TLS подготовлена для будущего переноса. [Архитектура и порядок переноса](HIGH-AVAILABILITY.md).

Docker разделяет процессы и полномочия, но root-доступ к VPS и Docker по-прежнему позволяет управлять всеми контейнерами. Будущие реальные ключи и основной резерв требуют отдельного контура безопасности.

## Первый запуск

Скопируйте финансовые исходники, package.json, package-lock.json, tsconfig.json, tsconfig.finance.json, `compose.finance.yaml`, `.dockerignore`, каталог `deployment/finance`, файлы `scripts/finance-*.ts` и `server-tests/finance` в `/opt/royal-finance`. Локальные `.env` и реальные ключи не копируются.

Команды на VPS:

```sh
cd /opt/royal-finance
python3 deployment/finance/create-secrets.py
docker compose -f compose.finance.yaml config --quiet
docker compose -f compose.finance.yaml build finance-migrate
docker compose -f compose.finance.yaml up -d --wait --wait-timeout 180 finance-gateway
docker compose -f compose.finance.yaml ps -a
```

Секреты создаются в `/opt/royal-finance-secrets`, вне исходников. Каталог доступен только root. Файлы имеют режим 0440: пароль администратора доступен группе 999, рабочий пароль и токен группе 1000. Это соответствует пользователям PostgreSQL и Node в используемых Debian-образах. При смене образов нужно проверить UID и GID. Скрипт не выводит значения и сохраняет существующие секреты.

Административный пароль монтируется только в базу и контейнер миграции. Рабочий API получает только пароль ограниченного логина `finance_app` и токен симуляции. Секреты читаются из файлов, а не записываются в переменные окружения контейнеров или в образ.

Для поступлений добавлен отдельный пароль `observer-password` и логин `finance_ingest`. Одноразовый наблюдатель с профилем `deposit-lab` получает только этот пароль. Он проверяет два лабораторных источника, тестовый токен, финальность и повторы, сохраняет события и курсор вместе с проводками. Лабораторный профиль использует файлы источников; подключение криптокошельков пользователей относится к следующему этапу. [Поступления в симуляторе сети](DEPOSITS.md).

Отдельно реализован постоянный наблюдатель публичной тестовой сети Nile: `royal-tron-reader`, конфигурация `deployment/finance/compose.tron-reader.yaml`. Он работает в режиме `watch-only`, сохраняет проверенные блоки и Transfer в схему `royal_tron_reader` единой PostgreSQL и не имеет финансовых полномочий или ключей. [Чтение тестовой сети и управление](DEPOSITS.md#постоянное-чтение-тестовой-сети-tron). Финансовый симулятор и наблюдатель обновляются отдельными образами.

Для двух управляемых тестовых адресов добавлен отдельный `royal-nile-creditor`, Compose `deployment/finance/compose.nile-creditor.yaml`. Он читает схему наблюдателя только для чтения, имеет только закрытую сеть PostgreSQL, не получает ключей и сохраняет подтвержденные поступления закрепленного тестового USDT в схему `royal_nile_deposits`. Баланс `USDT_NILE_TEST` не связан с `USDT_SIM`. [Публичный контракт, адреса, управление и ограничения](DEPOSITS.md#поступления-usdt-в-отдельный-баланс-nile).

Данные PostgreSQL находятся в постоянном томе `royal-finance-sim_finance_data`. Удаление тома удалит журнал и балансы. Для обычных обновлений том сохраняется.

## Проверка сервера

```sh
cd /opt/royal-finance
docker compose -f compose.finance.yaml exec -T -e FINANCE_API_URL=http://finance-gateway:2570 finance-api node dist-finance-tools/finance-smoke.js
docker network inspect royal-finance-sim_finance_private --format 'Internal={{.Internal}}'
docker compose -f compose.finance.yaml ps -a
```

Проверка создаёт два аккаунта с префиксом `servercheck_`, добавляет симулированный капитал и проходит пополнение, повтор запроса, перевод, игру, неопределённый вывод и его подтверждение. Проверяется запрет отмены неопределённого вывода и отказ без сервисного токена. Итоговые доступные остатки: 80 и 15 USDT_SIM, резервы равны нулю, сверка возвращает `ok: true`.

Каждый запуск добавляет новые симулированные операции в постоянную историю. Это проверка тестового контура, а не способ начисления реальных денег пользователям.

Каждый API доступен из своего контейнера через `http://127.0.0.1:2570`. Общий вход внутри финансовой сети: `http://finance-gateway:2570`. Имя `finance-api` используется балансировщиком для поиска экземпляров. Для административных запросов используйте `docker compose exec` с чтением токена из смонтированного файла. Токен даёт управление всем симулятором и не передаётся в браузер игрока.

`/healthz` проверяет доступность базы, разрешение записи, версию схемы и текущие полномочия рабочего логина. Он отклоняет подключение к standby, соединение только для чтения и опасное изменение прав после запуска. Авторизованные запросы API также проверяют права перед обработкой и при нарушении возвращают 503. Для запуска обязательны режим `simulation` и ограниченная роль базы. Контейнеры намеренно используют `NODE_ENV=development`, поскольку код запрещает работу финансового симулятора в production-режиме. Размещение на VPS не превращает симулятор в систему реальных платежей.

В схеме 3 таблица `account_totals` поддерживает итоги проводок триггерами. Отложенная проверка баланса использует эти итоги, полная сверка независимо пересчитывает историю. Для рабочих соединений PostgreSQL 17 установлены `statement_timeout=10s` и `transaction_timeout=15s`; второй ограничивает всю транзакцию, включая отложенные проверки при commit. Параметр `options` в URL базы запрещён, чтобы он не переопределял ограничение.

## Обновление

После синхронизации финансовых исходников:

```sh
cd /opt/royal-finance
sh deployment/finance/backup.sh
docker compose -f compose.finance.yaml build finance-migrate
docker compose -f compose.finance.yaml up -d --wait --wait-timeout 180 finance-gateway
docker compose -f compose.finance.yaml logs --tail=50 finance-api finance-gateway finance-migrate
```

Не используйте игровой compose-файл для обновления финансового контура. Новая версия мигратора повторно использует существующую схему и рабочую роль. Секреты не удаляются и не генерируются заново при обычном обновлении.

Текущая версия схемы 3. Миграция с версии 2 сохраняет счета, операции, адреса, события и курсор, добавляет `account_totals` и проверяет его по истории. На VPS отпечатки всех 12 прежних таблиц данных до и после миграции совпали; результат сохранён в `/opt/royal-finance-state/migration-v3.json`. Новые копии содержат 14 таблиц; проверка восстановления поддерживает также схемы 1 и 2 с 9 и 13 таблицами.

До перехода сохранены исходники `/opt/royal-finance-backups/before-hardening-source-20261006.tar.gz`, копия базы `finance-20261006T050227Z-429b79b7.dump` и образ `royal-finance-sim:before-hardening-20261006`. Этот образ поддерживает схему 2 и не запускается со схемой 3. После миграции исправления выполняются кодом с поддержкой схемы 3; возврат старой копии после новых операций требует согласованного переноса актуальных данных.

## Резервное копирование

```sh
cd /opt/royal-finance
sh deployment/finance/backup.sh
```

Скрипт создаёт согласованный PostgreSQL dump в `/opt/royal-finance-backups`, контрольные суммы и метаданные для полного тестового восстановления. На VPS включены часовые копии, ежедневное восстановление в изолированный контейнер и мониторинг каждую минуту. На сервере сохраняются копии за 14 дней.

На Mac настроены внешний контроль и зашифрованное копирование каждые 5 минут, с хранением за 30 дней. Агент работает, когда компьютер включён и не спит. Полное восстановление проверено как из серверной копии, так и из копии, скачанной и расшифрованной на Mac. Расписание, управление, расположение ключа и оставшиеся этапы отказоустойчивости описаны в [инструкции эксплуатации](OPERATIONS.md).

Лабораторный журнал `USDT_NILE_TEST` также имеет автоматические зашифрованные копии на Mac с полным аудитом восстановления. Отдельный одноразовый контейнер сверяет токены с обязательствами каждые 5 минут, без полномочий записи или подписи. [Сверка Nile](DEPOSITS.md#сверка-сетевых-токенов-и-журнала-nile).
